# Ticket AI Worker

Асинхронный микросервис для обработки тикетов через Dify (External RAG, Classification)

## Архитектура

Микросервис реализует паттерн **External RAG**, где воркер сам выполняет поиск контекста через Dify API, используя Admin Key, а затем вызывает Workflow для генерации финального ответа.

### Схема потоков данных

```
Main App -> Redis (BullMQ) -> AI Worker <-> Dify API
```

**Очереди:**

- **`ai-entry-queue` (Entry Point)** — Единая точка входа для всех задач. Внешние сервисы должны отправлять задачи только в эту очередь. Router Worker автоматически распределяет задачи по внутренним очередям.
- **`ai-interactive-queue` (Fast Lane)** — Внутренняя очередь для интерактивных задач: чат, перевод, анализ, RAG-генерация (высокий concurrency)
- **`ai-background-queue` (Slow Lane)** — Внутренняя очередь для фоновых задач: загрузка файлов, архивация, системная синхронизация (низкий concurrency, Rate Limiter)
- **`ai-results-queue` (Output)** — Единый канал для возврата результатов

Подробное описание архитектуры и спецификации см. в `about/about_project.md`.

# Документация по интеграции сервиса Ticket AI

Сервис работает асинхронно через Redis (BullMQ). Архитектура построена на принципе «Поставщик (Producer) -> Потребитель (Consumer)» с гарантированным возвратом контекста вызывающей стороне.

## 1. Общая схема взаимодействия

1.  **Отправка (Request):** Ваше приложение отправляет задачу в очередь **`ai-entry-queue`**.
    
2.  **Маршрутизация:** Сервис определяет тип задачи и направляет её в нужный поток обработки (Fast Lane или Slow Lane).
    
3.  **Результат (Response):** После обработки (или при возникновении ошибки) сервис кладет результат в очередь **`ai-results-queue`**.
    

### Формат задачи (Job Request)

При добавлении задачи в BullMQ (`queue.add`) необходимо передать следующие поля:

-   **Name** (`string`, обязательное): Идентификатор команды (например, `CMD_GEN_RESPONSE`).
    
-   **Data** (`object`, обязательное): Тело задачи, содержащее два ключевых раздела:
    
    -   **`...бизнес-параметры`**: Поля, специфичные для конкретной команды (например, `query`, `orgId`).
        
    -   **`meta`** (`object`, опциональное): **Контейнер контекста (Pass-through)**. Любые поля, переданные в этом объекте, сервис **вернет обратно в ответе без изменений**. Сервис не валидирует и не использует эти данные для логики, он просто проносит их через весь пайплайн. _Используйте это для передачи:_ `socketId`, `userId`, `callbackUrl`, `internalRequestId` и любых других данных, необходимых вам для связывания асинхронного ответа с запросом.
        

### Формат ответа (Job Result)

Результат в очереди `ai-results-queue` всегда имеет унифицированную структуру. Объект `meta` в ответе — это слияние ваших исходных метаданных и системной телеметрии.

**Пример ответа (JSON) с комментариями:**

JSON

    {
      "success": true, // [Boolean] Общий статус операции. true - успех, false - ошибка.
    
      "meta": {
        // --- ВАШИ ДАННЫЕ (вернулись без изменений) ---
        "traceId": "req-123-abc",      // [String] Ваш ID запроса для сквозной трассировки (рекомендуется передавать).
        "userId": "user-55",           // [String] Пример вашего поля: ID пользователя, инициировавшего запрос.
        "socketId": "ws-888",          // [String] Пример вашего поля: ID сокета для ответа фронтенду.
        "customTag": "dashboard-ui",   // [String] Любое другое поле, которое вы передали в запросе.
    
        // --- СИСТЕМНЫЕ ДАННЫЕ (добавлены сервисом) ---
        "timestamp": 1715000000123,    // [Number] Unix timestamp момента формирования ответа.
        "processingTimeMs": 1450,      // [Number] Время выполнения задачи в миллисекундах.
        "jobId": "25",                 // [String] ID задачи внутри BullMQ.
        "usage": {                     // [Object] Информация о расходе токенов LLM (если применимо).
          "total_tokens": 150,         // [Number] Общее количество потраченных токенов.
          "stages": [                  // [Array] Детализация по этапам (например, упрощение запроса + генерация).
            {
              "prompt_tokens": 50,
              "completion_tokens": 100,
              "model": "gpt-4"
            }
          ]
        }
      },
    
      "data": {
        // [Object] Бизнес-данные успешного ответа (заполняется только если success: true).
        "content": "Ответ на ваш вопрос...", // Основной результат (текст, перевод, анализ).
        "sources": [...]                     // Дополнительные данные (источники, скоры и т.д.).
      },
    
      "error": {
        // [Object] Детали ошибки (заполняется только если success: false).
        "code": "KB_NOT_FOUND",        // [String] Машиночитаемый код ошибки для логики на клиенте.
        "message": "Knowledge base...",// [String] Читаемое описание ошибки.
        "retryable": false,            // [Boolean] Стоит ли пытаться повторить запрос автоматически.
        "details": "..."               // [String] Дополнительная техническая информация (опционально).
      }
    }

Команда

Краткое описание

**`CMD_GEN_RESPONSE`**

Генерация ответа на вопрос пользователя с использованием базы знаний (RAG).

**`CMD_ANALYZE_NEW_TICKET`**

Анализ входящего тикета: определение темы и тональности (Sentiment Analysis).

**`CMD_TRANSLATE`**

Перевод текста на указанный язык.

**`CMD_KB_LIST_FILES`**

Получение списка файлов, загруженных в базу знаний организации.

**`CMD_KB_DELETE_FILE`**

Удаление файла из базы знаний.

**`CMD_KB_ADD_FILE`**

Загрузка и индексация файла в базу знаний (через URL).

**`CMD_ARCHIVE_TICKET`**

Суммаризация истории завершенного тикета и сохранение её в базу знаний.

**`CMD_CLEANUP_ORG`**

Полное удаление всех данных организации (баз знаний и кэша).

**`CMD_SYS_RESYNC_CACHE`**

Принудительная синхронизация системного кэша Redis с состоянием в Dify.


## Команда: `CMD_ANALYZE_NEW_TICKET`

**Назначение:** Выполняет интеллектуальный анализ текста нового обращения (тикета). Использует LLM для классификации тональности сообщения (Sentiment Analysis) и генерации краткого заголовка (Summary).

**Очередь:** `ai-interactive-queue` (Fast Lane).

* * *

### 1\. Параметры запроса (Job Request)

При формировании задачи в объекте `data` используются следующие параметры:

-   **`content`** (строка, **обязательно**)
    
    -   Основной текст обращения пользователя, который необходимо проанализировать.
        
    -   _Алиасы (альтернативные ключи, поддерживаемые кодом):_ `text`, `query`.
        
-   **`targetLang`** (строка, опционально)
    
    -   Код языка, на котором нейросеть должна вернуть сгенерированный заголовок (`title`).
        
    -   _Значение по умолчанию:_ `'en'` (если параметр не передан, заголовок вернется на английском языке).
        
    -   _Алиасы:_ `lang`, `targetLanguage`, `params.targetLang`.
        
-   **`meta`** (объект, опционально)
    
    -   Контейнер для сквозной передачи контекста. Любые данные, переданные здесь, вернутся в ответе без изменений.
        

#### Пример корректного запроса

JavaScript

    {
      "name": "CMD_ANALYZE_NEW_TICKET",
      "data": {
        // [Обязательно] Текст тикета для анализа
        "content": "У нас упал прод, 500 ошибка на главной! Срочно!",
    
        // [Опционально] Язык для заголовка. Если не передать, будет "en".
        "targetLang": "en",
    
        // [Опционально] Ваши данные для связывания ответа с запросом
        "meta": {
          "internalId": "ticket-777", // ID тикета в вашей системе
          "socketId": "ws-client-12"  // ID сокета оператора
        }
      }
    }

* * *

### 2\. Параметры успешного ответа (Job Result)

В случае успешного выполнения (`success: true`) результат содержит следующие поля:

**Объект `data` (Бизнес-данные):**

-   **`title`** (строка)
    
    -   Краткий, емкий заголовок тикета, сгенерированный ИИ на запрошенном языке.
        
-   **`sentiment`** (строка)
    
    -   Оценка эмоциональной окраски сообщения.
        
    -   _Возможные значения:_
        
        -   `'positive'` — Позитивный/благодарственный тон.
            
        -   `'neutral'` — Нейтральный/информационный тон.
            
        -   `'negative'` — Негативный/требовательный тон (жалоба).
            

**Объект `meta` (Системные данные):**

-   **`usage`** (объект)
    
    -   Информация о количестве потраченных токенов LLM.
        
    -   Содержит поле `total_tokens` (общее количество) и массив `stages` (детализация по этапам).
        
-   **`processingTimeMs`** (число)
    
    -   Время выполнения задачи в миллисекундах.
        
-   **`...ваши поля`**
    
    -   Все поля, которые вы передали в `meta` при запросе (например, `internalId`).
        

#### Пример успешного ответа

JavaScript

    {
      "success": true,
      "data": {
        // Сгенерированный заголовок (на английском, т.к. в запросе targetLang="en")
        "title": "Production 500 Error on Main Page",
        
        // Определенная тональность
        "sentiment": "negative"
      },
      "meta": {
        // Ваши данные из запроса (вернулись как есть)
        "internalId": "ticket-777",
        "socketId": "ws-client-12",
    
        // Системные данные
        "traceId": "req-abc-123",
        "processingTimeMs": 1200,
        "usage": {
          "total_tokens": 150,
          "stages": [
            {
              "prompt_tokens": 100,
              "completion_tokens": 50,
              "model": "gpt-4"
            }
          ]
        }
      }
    }

* * *

### 3\. Возможные ошибки

Если выполнение не удалось (`success: false`), в поле `error.code` вернется один из следующих кодов:

-   **`DIFY_API_ERROR`**
    
    -   _Причина:_ Внешний сервис (Dify) вернул ошибку (4xx или 5xx) или недоступен.
        
    -   _Действие:_ Можно повторить запрос, если ошибка сетевая.
        
-   **`INTERNAL_ERROR`**
    
    -   _Причина:_
        
        1.  LLM вернула ответ в неверном формате (невалидный JSON).
            
        2.  В ответе LLM отсутствуют обязательные поля `title` или `sentiment`.
            
        3.  Ошибка конфигурации (не задан API-ключ).
            
    -   _Действие:_ Повторный запрос вряд ли поможет без вмешательства разработчиков (проверка промптов или ключей).
        
-   **`TIMEOUT`**
    
    -   _Причина:_ Истекло время ожидания ответа от нейросети (по умолчанию 60 секунд).
        
    -   _Действие:_ Можно повторить запрос.
        
-   **`NETWORK_ERROR`**
    
    -   _Причина:_ Проблема с сетевым подключением к API провайдера.
        
    -   _Действие:_ Можно повторить запрос.

## Команда: `CMD_GEN_RESPONSE`

**Назначение:** Генерация ответа на вопрос пользователя с использованием базы знаний организации (Retrieval Augmented Generation). Сервис выполняет поиск релевантной информации в административной базе и истории тикетов, формирует контекст и запрашивает ответ у LLM через Dify Workflow. На этот момент должны быть загружены хотя бы один файл в базу знаний или архивный тикет.. 

**Очередь:** `ai-interactive-queue` (Fast Lane).

* * *

### 1\. Параметры запроса (Job Request)

При формировании задачи в объекте `data` используются следующие параметры:

-   **`orgId`** (строка, **обязательно**)
    
    -   Уникальный идентификатор организации. Используется для определения, в какой базе знаний искать информацию.
        
    -   Если базы знаний для этой организации еще нет, сервис попытается создать её автоматически (Lazy Loading) но она будет пустой.
        
-   **`query`** (строка, **обязательно**)
    
    -   Текст вопроса пользователя.
        
-   **`history`** (массив или строка, опционально)
    
    -   История переписки для сохранения контекста диалога.
        
    -   _Формат:_ Может быть передана как массив объектов `[{ role: 'user', content: '...' }, ...]` или как готовая строка Markdown где распределение что сказал юзер и что написал кто то из саппорта отформатировано произвольно в надежде что модель разберётся.
        
    -   _Примечание:_ Если история слишком длинная, сервис автоматически обрежет старые сообщения, чтобы уложиться в лимиты модели. Первый пост считается самым старым - в конце последние. Рекомендуем удалять из истории сообщений вопрос юзера на который даётся ответ (что бы его не было и в истории на последнем месте и в квери)
        
-   **`lang`** (строка, опционально)
    
    -   Язык ответа (например, `'ru'`, `'en'`). Передается в LLM Workflow как переменная управления языком.
        
-   **`meta`** (объект, опционально)
    
    -   Контейнер для сквозной передачи контекста. Любые данные, переданные здесь, вернутся в ответе без изменений.
        

#### Пример корректного запроса

JavaScript

    {
      "name": "CMD_GEN_RESPONSE",
      "data": {
        // [Обязательно] ID организации для выбора базы знаний
        "orgId": "org-100",
    
        // [Обязательно] Вопрос пользователя
        "query": "Как настроить VPN подключение?",
    
        // [Опционально] История диалога
        "history": [
          { "role": "user", "content": "У меня не работает сеть." },
          { "role": "assistant", "content": "Какую ошибку вы видите?" }
        ],
    
        // [Опционально] Предпочтительный язык ответа
        "lang": "ru",
    
        // [Опционально] Ваши данные
        "meta": {
          "chatId": "chat-555",
          "userId": "user-777"
        }
      }
    }

* * *

### 2\. Параметры успешного ответа (Job Result)

В случае успешного выполнения (`success: true`) результат содержит:

**Объект `data` (Бизнес-данные):**

-   **`content`** (строка)
    
    -   Текст ответа, сгенерированный нейросетью.
        
-   **`sources`** (массив объектов)
    
    -   Список источников (документов), которые были использованы для формирования ответа. Содержит названия документов, ID и степень релевантности (если доступна).
        
-   **`retrievedContext`** (массив объектов)
    
    -   Сырые фрагменты текста (chunks), найденные в базе знаний по запросу.
        
    -   Полезно для отладки или отображения пользователю цитат ("На основании чего был дан ответ").
        
    -   Каждый объект содержит поля: `content` (текст), `score` (релевантность), `source` (источник: `admin_kb`(из файлов) или `history_kb`(из архивных тикетов)).
        

**Объект `meta` (Системные данные):**

-   **`usage`** (объект)
    
    -   Детализация расхода токенов. Включает сумму токенов за все этапы (упрощение запроса + генерация ответа).
        
    -   Поле `stages` показывает расход по каждому шагу пайплайна.
        
-   **`processingTimeMs`** (число)
    
    -   Время выполнения всего пайплайна RAG.
        
-   **`...ваши поля`**
    
    -   Все поля из запроса (например, `chatId`).
        

#### Пример успешного ответа

JavaScript

    {
      "success": true,
      "data": {
        // Сгенерированный ответ
        "content": "Для настройки VPN откройте приложение Cisco AnyConnect...",
    
        // Использованные источники
        "sources": [
          {
            "document_name": "Инструкция VPN.pdf",
            "document_id": "doc-abc-123",
            "score": 0.85
          }
        ],
    
        // Найденные фрагменты (для отладки или выводк админу как пруфы - на основе каких именно данных модель строила свой ответ)
        "retrievedContext": [
          {
            "content": "...нажмите кнопку Connect в окне AnyConnect...",
            "score": 0.85,
            "source": "admin_kb",
            "documentName": "Инструкция VPN.pdf"
          }
        ]
      },
      "meta": {
        // Ваши данные
        "chatId": "chat-555",
        "userId": "user-777",
    
        // Системные метрики
        "traceId": "trace-999",
        "processingTimeMs": 2500,
        "usage": {
          "total_tokens": 450,
          "stages": [
            { "type": "simplification", "total_tokens": 50 },
            { "type": "generation", "total_tokens": 400 }
          ]
        }
      }
    }

* * *

### 3. Возможные ошибки

Если выполнение не удалось (`success: false`), в поле `error.code` вернется один из следующих кодов:

-   **`DIFY_API_ERROR`**
    
    -   _Причина:_ Ошибка при взаимодействии с API Dify (поиск в базе, генерация ответа, запуск workflow). Может возникать, если ключи API неверны или сервис перегружен.
        
    -   _Действие:_ Часто является временной проблемой (retryable), если код ответа 5xx.
        
-   **`INTERNAL_ERROR`**
    
    -   _Причина:_ Системная ошибка сервиса (например, сбой при сборке контекста или отсутствуют обязательные настройки).
        
    -   _Действие:_ Требуется проверка логов сервиса.
        
-   **`TIMEOUT`**
    
    -   _Причина:_ LLM или поиск в базе знаний заняли больше времени, чем разрешено таймаутом (60 сек).
        
    -   _Действие:_ Можно повторить запрос.
        
-   **`NETWORK_ERROR`**
    
    -   _Причина:_ Проблемы с сетевой связностью между воркером и API провайдера.
        
    -   _Действие:_ Можно повторить запрос.
        

> **Примечание:** Ошибка `KB_NOT_FOUND` для этой команды возникает крайне редко, так как сервис автоматически пытается создать (ensures) базу знаний при её отсутствии. Если создание не удалось, вернется `DIFY_API_ERROR`.

## Команда: `CMD_TRANSLATE`

**Назначение:** Выполняет перевод текста на указанный целевой язык. Использует специализированный Dify Workflow (на базе LLM) для обеспечения высокого качества перевода с сохранением контекста и стиля.

**Очередь:** `ai-interactive-queue` (Fast Lane).

* * *

### 1. Параметры запроса (Job Request)

При формировании задачи в объекте `data` используются следующие параметры:

-   **`content`** (строка, **обязательно**)
    
    -   Исходный текст, который необходимо перевести.
        
    -   _Алиасы (альтернативные ключи):_ `text`.
        
-   **`targetLang`** (строка, опционально)
    
    -   Код языка, на который нужно перевести текст (например, `'en'`, `'es'`, `'de'`).
        
    -   _Значение по умолчанию:_ `'en'` (если параметр не передан, перевод будет на английский).

## Команда: `CMD_KB_ADD_FILE`

**Назначение:** Загрузка файла в административную базу знаний организации. Сервис скачивает файл по переданной ссылке, загружает его в Dify и запускает процесс индексации (Vector Embedding). Если Dify не может обработать файл как бинарный (например, специфичный формат), сервис автоматически пробует извлечь текст и загрузить его как текстовый документ (fallback).

**Очередь:** `ai-background-queue` (Slow Lane). _Примечание:_ Обработка может занимать время (от секунд до минут в зависимости от размера файла).

* * *

### 1\. Параметры запроса (Job Request)

При формировании задачи в объекте `data` используются следующие параметры:

-   **`orgId`** (строка, **обязательно**)
    
    -   Уникальный идентификатор организации.
        
    -   Если базы знаний нет, она будет создана автоматически (Lazy Loading).
        
-   **`fileUrl`** (строка, **обязательно**)
    
    -   Прямая публичная ссылка на скачивание файла.
        
    -   Сервис должен иметь возможность скачать файл по этой ссылке (HTTP GET).
        
-   **`fileName`** (строка, **обязательно**)
    
    -   Имя файла с расширением (например, `instruction.pdf`, `faq.docx`).
        
    -   Важно передавать правильное расширение, так как Dify использует его для выбора парсера.
        
-   **`meta`** (объект, опционально)
    
    -   Контейнер для сквозной передачи контекста.
        

#### Пример корректного запроса

JavaScript

    {
      "name": "CMD_KB_ADD_FILE",
      "data": {
        // [Обязательно] ID организации

        // [Обязательно] Имя файла

          "uploaderId": "admin-01",
          "sourceSystem": "cms"
        }
      }
    }

В случае успешного выполнения (`success: true`) результат содержит:

**Объект `data` (Бизнес-данные):**

-   **`documentId`** (строка)
    
    -   Уникальный ID созданного документа в Dify.
        
-   **`status`** (строка)
    
    -   Текущий статус обработки. Обычно `'indexing'` (индексация запущена) или `'completed'` (завершена).
        
-   **`fileName`** (строка)

-   **`orgId`** (строка)
    
    -   ID организации.
        
-   **`fallback`** (строка, опционально)
    
    -   Если поле присутствует (значение `'createDocumentByText'`), это означает, что прямая загрузка файла не удалась, и сервис применил механизм fallback: скачал файл, прочитал его как текст и загрузил как текстовый фрагмент.
        

**Объект `meta` (Системные данные):**

-   **`usage`** (объект, опционально)
    
    -   Если индексация успела завершиться в процессе выполнения задачи, здесь будет информация о количестве токенов, потраченных на эмбеддинг документа.
        
-   **`processingTimeMs`** (число)
    
    -   Время выполнения загрузки.
        
-   **`...ваши поля`**
    
    -   Все поля из запроса.

### 3\. Возможные ошибки

Если выполнение не удалось (`success: false`), в поле `error.code` вернется один из следующих кодов:

-   **`FILE_TOO_LARGE`**
    
    -   _Причина:_ Размер файла по ссылке превышает жесткий лимит сервиса (по умолчанию 50MB). Загрузка прерывается для защиты памяти.
        
    -   _Действие:_ Уменьшить файл или разбить на части.
        
-   **`DOWNLOAD_ERROR`**
    
    -   _Причина:_ Не удалось скачать файл по `fileUrl`. Возможные причины: 404 Not Found, таймаут соединения, ошибка DNS.
        
    -   _Действие:_ Проверить доступность ссылки.
        
-   **`FILE_TOO_LARGE_FOR_FALLBACK`**
    
    -   _Причина:_ Прямая загрузка не удалась, а при попытке прочитать файл в память (fallback) выяснилось, что он больше лимита для текстовой обработки (5MB).
        
    -   _Действие:_ Файл слишком сложный для автоматического парсинга, требуется конвертация.
        
-   **`DIFY_API_ERROR`**
    
    -   _Причина:_ Dify отклонил файл (неподдерживаемый формат, внутренняя ошибка).
        
    -   _Действие:_ Проверить логи или формат файла.
        
-   **`TIMEOUT`**
    
    -   _Причина:_ Процесс скачивания и загрузки занял слишком много времени.
        
-   **`NETWORK_ERROR`**
    
    -   _Причина:_ Сетевая ошибка при взаимодействии с Dify.

## Команда: `CMD_ARCHIVE_TICKET`

**Назначение:** Архивация завершенного тикета. Сервис выполняет следующие действия:

1.  Анализирует полную историю переписки.
    
2.  С помощью LLM генерирует краткое содержание (саммари) решения проблемы.
    
3.  Сохраняет это саммари как новый документ в **историческую базу знаний** (History KB) организации. Это позволяет использовать данный опыт для ответов на будущие вопросы (через RAG).
    

**Очередь:** `ai-background-queue` (Slow Lane).

* * *

### 1\. Параметры запроса (Job Request)

При формировании задачи в объекте `data` используются следующие параметры:

-   **`orgId`** (строка, **обязательно**)
    
    -   Уникальный идентификатор организации.
        
    -   Используется для выбора или создания исторической базы знаний (`KB_HISTORY_*`).
        
-   **`fullTicketHistory`** (массив или строка, **обязательно**)
    
    -   Полная история переписки по тикету.
        
    -   _Формат:_
        
        -   **Массив объектов:** `[{ role: 'user', content: '...' }, { role: 'assistant', content: '...' }]` (рекомендуемый формат).
            
        -   **Строка:** Текстовое представление диалога (Markdown или Plain Text).
            
    -   Сервис автоматически отформатирует этот массив в текст перед отправкой в LLM.
        
-   **`lang`** (строка, опционально)
    
    -   Язык, на котором должно быть составлено саммари (например, `'ru'`, `'en'`).
        
    -   _Примечание:_ Если не указан, LLM обычно использует язык самого тикета или настройку по умолчанию в Dify Workflow.
        
-   **`meta`** (объект, опционально)
    
    -   Контейнер для сквозной передачи контекста.
        
    -   **Рекомендация:** Передавайте сюда поле `ticketId`, так как оно используется для формирования имени документа в базе знаний (см. ниже).
        

#### Пример корректного запроса

JavaScript

    {
      "name": "CMD_ARCHIVE_TICKET",
      "data": {
        // [Обязательно] ID организации
        "orgId": "org-555",
    
        // [Обязательно] История тикета
        "fullTicketHistory": [
          { "role": "user", "content": "Принтер жует бумагу." },
          { "role": "assistant", "content": "Попробуйте очистить лоток." },
          { "role": "user", "content": "Помогло, спасибо!" }
        ],
    
        // [Опционально] Язык саммари
        "lang": "ru",
    
        // [Опционально] Ваши данные
        "meta": {
          "ticketId": "T-100500", // Важно для имени документа
          "closedBy": "operator-42"
        }
      }
    }

* * *

### 2\. Параметры успешного ответа (Job Result)

В случае успешного выполнения (`success: true`) результат содержит:

**Объект `data` (Бизнес-данные):**

-   **`documentId`** (строка)
    
    -   ID созданного документа (саммари) в базе знаний Dify.
        
-   **`docName`** (строка)
    
    -   Название созданного документа.
        
    -   _Формат:_ `"Ticket #{ticketId}"` (если `ticketId` был передан в `meta`) или `"Ticket #{jobId}"` (если нет).
        
-   **`orgId`** (строка)
    
    -   ID организации.
        

**Объект `meta` (Системные данные):**

-   **`usage`** (объект)
    
    -   Информация о расходе токенов. Суммирует затраты на:
        
        1.  Генерацию саммари (Workflow).
            
        2.  Индексацию созданного документа (Embedding).
            
-   **`processingTimeMs`** (число)
    
    -   Время выполнения архивации.
        
-   **`...ваши поля`**
    
    -   Все поля из запроса (включая `ticketId`).
        

#### Пример успешного ответа

JavaScript

    {
      "success": true,
      "data": {
        "documentId": "doc-summary-uuid-999",
        "docName": "Ticket #T-100500",
        "orgId": "org-555"
      },
      "meta": {
        // Ваши данные
        "ticketId": "T-100500",
        "closedBy": "operator-42",
    
        // Системные метрики
        "traceId": "req-archive-01",
        "processingTimeMs": 4200,
        "usage": {
          "total_tokens": 300,
          "stages": [
            { "model": "gpt-4", "total_tokens": 250, "type": "summary" },
            { "model": "text-embedding-3", "total_tokens": 50, "type": "indexing" }
          ]
        }
      }
    }

* * *

### 3\. Возможные ошибки

Если выполнение не удалось (`success: false`), в поле `error.code` вернется один из следующих кодов:

-   **`DIFY_API_ERROR`**
    
    -   _Причина:_ Ошибка Dify при генерации саммари (Workflow) или при создании документа.
        
    -   _Действие:_ Можно повторить запрос.
        
-   **`INTERNAL_ERROR`**
    
    -   _Причина:_
        
        1.  Отсутствуют обязательные поля `orgId` или `fullTicketHistory`.
            
        2.  LLM вернула пустой результат саммари.
            
        3.  Ошибка конфигурации ключей (`DIFY_KEY_SUMMARIZER` или `DIFY_KEY_ADMIN`).
            
-   **`TIMEOUT`**
    
    -   _Причина:_ Процесс суммаризации или индексации занял слишком много времени.
        
-   **`NETWORK_ERROR`**
    
    -   _Причина:_ Проблемы с сетью.

## Команда: `CMD_CLEANUP_ORG`

**Назначение:** Полная очистка данных организации. Сервис выполняет удаление административной базы знаний (Admin KB) и исторической базы знаний (History KB) в Dify, а также инвалидирует (удаляет) кэш связанных идентификаторов в Redis. Обычно используется при удалении аккаунта клиента или для сброса данных (GDPR compliance).

**Очередь:** `ai-background-queue` (Slow Lane).

* * *

### 1\. Параметры запроса (Job Request)

При формировании задачи в объекте `data` используются следующие параметры:

-   **`orgId`** (строка, **обязательно**)
    
    -   Уникальный идентификатор организации, данные которой нужно удалить.
        
-   **`meta`** (объект, опционально)
    
    -   Контейнер для сквозной передачи контекста (например, `initiatorId`, `auditLogId`).
        

#### Пример корректного запроса

JavaScript

    {
      "name": "CMD_CLEANUP_ORG",
      "data": {
        // [Обязательно] ID организации
        "orgId": "org-to-delete-555",
    
        // [Опционально] Ваши данные
        "meta": {
          "initiatorId": "system-admin",
          "reason": "gdpr-request"
        }
      }
    }

* * *

### 2\. Параметры успешного ответа (Job Result)

В случае успешного выполнения (`success: true`) результат содержит:

**Объект `data` (Бизнес-данные):**

-   **`orgId`** (строка)
    
    -   ID организации.
        
-   **`deleted`** (объект)
    
    -   Содержит идентификаторы удаленных баз знаний:
        
        -   `adminKbId` (строка или `null`): ID удаленной админской базы.
            
        -   `historyKbId` (строка или `null`): ID удаленной исторической базы.
            
    -   _Примечание:_ Если какая-то из баз не существовала, значение может быть `null`, но операция считается успешной.
        

**Объект `meta` (Системные данные):**

-   **`processingTimeMs`** (число)
    
    -   Время выполнения очистки.
        
-   **`...ваши поля`**
    
    -   Все поля из запроса.
        

#### Пример успешного ответа

JavaScript

    {
      "success": true,
      "data": {
        "orgId": "org-to-delete-555",
        "deleted": {
          "adminKbId": "dataset-uuid-1",
          "historyKbId": "dataset-uuid-2"
        }
      },
      "meta": {
        // Ваши данные
        "initiatorId": "system-admin",
        "reason": "gdpr-request",
    
        // Системные метрики
        "traceId": "req-clean-99",
        "processingTimeMs": 1500
      }
    }

* * *

### 3\. Возможные ошибки

Если выполнение не удалось (`success: false`), в поле `error.code` вернется один из следующих кодов:

-   **`KB_NOT_FOUND`**
    
    -   _Причина:_ Для указанной `orgId` не найдены записи о базах знаний в кэше. Это означает, что удалять нечего (или данные уже удалены).
        
    -   _Действие:_ Обычно можно считать это эквивалентом успеха, если цель — отсутствие данных.
        
-   **`DIFY_API_ERROR`**
    
    -   _Причина:_ Критическая ошибка Dify API при попытке удаления датасета (отличная от 404).
        
    -   _Действие:_ Можно повторить запрос.
        
    -   _Примечание:_ Если Dify возвращает 404 (датасет не найден), сервис **не** считает это ошибкой и продолжает выполнение.
        
-   **`INTERNAL_ERROR`**
    
    -   _Причина:_ Ошибка конфигурации (нет ключа `DIFY_KEY_ADMIN`) или внутренней логики.
        
-   **`TIMEOUT`**
    
    -   _Причина:_ Удаление заняло слишком много времени.
        
-   **`NETWORK_ERROR`**
    
    -   _Причина:_ Проблемы с сетевым подключением.

## Команда: `CMD_SYS_RESYNC_CACHE`

**Назначение:** Системная команда для принудительной синхронизации кэша Redis с текущим состоянием Dify. Сервис скачивает список всех баз знаний из Dify, парсит их названия (по шаблонам `KB_ADMIN_*` и `KB_HISTORY_*`) и обновляет маппинг `orgId -> datasetId` в Redis. Используется администраторами для восстановления целостности данных (например, после ручного удаления баз в Dify или при "холодном" старте с пустым кэшем).

**Очередь:** `ai-background-queue` (Slow Lane).

* * *

### 1\. Параметры запроса (Job Request)

Эта команда не требует специфических бизнес-параметров в `data`.

-   **`meta`** (объект, опционально)
    
    -   Контейнер для сквозной передачи контекста (например, `adminId`, `reason`).
        

#### Пример корректного запроса

JavaScript

    {
      "name": "CMD_SYS_RESYNC_CACHE",
      "data": {
        // Параметры не требуются, передаем пустой объект или только meta
        "meta": {
          "initiator": "devops-script",
          "reason": "manual-resync"
        }
      }
    }

* * *

### 2\. Параметры успешного ответа (Job Result)

В случае успешного выполнения (`success: true`) результат содержит статистику синхронизации:

**Объект `data` (Бизнес-данные):**

-   **`processed`** (число)
    
    -   Общее количество датасетов, полученных и обработанных из Dify.
        
-   **`updated`** (число)
    
    -   Количество организаций, для которых была обновлена или подтверждена информация в кэше.
        

**Объект `meta` (Системные данные):**

-   **`processingTimeMs`** (число)
    
    -   Время выполнения синхронизации.
        
-   **`...ваши поля`**
    
    -   Все поля из запроса.
        

#### Пример успешного ответа

JavaScript

    {
      "success": true,
      "data": {
        "processed": 150, // Всего найдено баз в Dify
        "updated": 75     // Обновлено записей для 75 организаций
      },
      "meta": {
        // Ваши данные
        "initiator": "devops-script",
        "reason": "manual-resync",
    
        // Системные метрики
        "traceId": "sys-sync-001",
        "processingTimeMs": 5200
      }
    }

* * *

### 3\. Возможные ошибки

Если выполнение не удалось (`success: false`), в поле `error.code` вернется один из следующих кодов:

-   **`DIFY_API_ERROR`**
    
    -   _Причина:_ Ошибка при получении списка датасетов из Dify (например, неверный Admin Key или недоступность API).
        
    -   _Действие:_ Проверить настройки подключения к Dify.
        
-   **`INTERNAL_ERROR`**
    
    -   _Причина:_ Ошибка записи в Redis.
        
-   **`TIMEOUT`**
    
    -   _Причина:_ Синхронизация заняла слишком много времени (если баз очень много).
        
    -   _Действие:_ Можно увеличить таймауты или повторить запрос.
        
-   **`NETWORK_ERROR`**
    
    -   _Причина:_ Проблемы с сетью.

## HTTP API: Healthcheck

**Назначение:** Проверка работоспособности сервиса ("живучесть"). Используется Kubernetes (liveness/readiness probes), балансировщиками нагрузки или мониторингом для проверки, что сервис готов принимать задачи. Эндпоинт проверяет соединение с Redis, доступность Dify API и статус воркеров очередей.

**URL:** `GET /health` **Порт:** `3000` (по умолчанию, см. `HEALTHCHECK_PORT` в конфиге).

### 1\. Формат запроса

Запрос не требует параметров или тела.

HTTP

    GET /health HTTP/1.1
    Host: ticket-ai-service:3000

### 2\. Формат ответа

#### Успешный ответ (HTTP 200 OK)

Возвращается, если все критические компоненты (Redis, Dify, Workers) работают исправно.

JSON

      "status": "healthy",

      "checks": {
        "redis": {

          },
          "slowLane": {
            "status": "ok",
            "message": "Worker is running",

          }
        }
      }
    }

#### Ответ при сбое (HTTP 503 Service Unavailable)

Возвращается, если хотя бы один компонент недоступен (например, отпал Redis).

JSON

## Быстрый старт (Local Development)

1. **Скопируйте `.env.example` в `.env` и заполните ключи:**

```bash
cp .env.example .env
```

2. **Установите зависимости:**

```bash
npm install
```

3. **Запустите проект с автоматической проверкой и запуском Dify:**

```bash
# Режим разработки (с автоперезагрузкой)
npm run dev:with-dify-check

# Или production режим
npm run start:with-dify-check
```

Эти команды автоматически:
- Проверяют доступность Dify API
- Если Dify недоступен, запускают необходимые сервисы через `docker-compose`
- Ждут пока Dify станет доступен
- Запускают воркер

**Альтернативные варианты запуска:**

```bash
# Запуск без проверки Dify (если Dify уже запущен или не нужен)
npm run dev:skip-dify
npm run start:skip-dify

# Обычный запуск (без автоматической проверки Dify)
npm run dev
npm start
```

**Ручной запуск всех сервисов:**

Если вы предпочитаете запускать сервисы вручную:

```bash
# Запустить все сервисы Docker
docker-compose up -d

# Это запустит:
# - Redis на порту 6379
# - PostgreSQL для Dify (внутренний порт)
# - Dify API на порту 5001
# - Dify Web на порту 3000 (веб-интерфейс)
# - Dify Plugin Daemon (сервис для управления плагинами)

# Затем запустить воркер
npm run dev
```

4. **Инициализируйте Dify (при первом запуске):**

Откройте браузер и перейдите на `http://localhost:3000/install` для первоначальной настройки Dify.

5. **Запустите тесты:**

```bash
npm test
```

### Получение DIFY_KEY_ADMIN в Dify

`DIFY_KEY_ADMIN` — это API ключ с правами **Dataset Operator** или **Admin** для управления базами знаний (knowledge bases/datasets). Он используется для:
- Создания и удаления датасетов (`/datasets`)
- Загрузки файлов в датасеты (`/datasets/{id}/document/create_by_file`)
- Создания документов из текста (`/datasets/{id}/document/create_by_text`)
- Поиска в базах знаний (`/datasets/{id}/retrieve`)

**Пошаговая инструкция:**

1. **Откройте веб-интерфейс Dify:**
   - Перейдите на `http://localhost:3000` (после запуска `docker-compose up -d`)
   - Войдите в систему

2. **Найдите раздел для создания API ключа:**
   
   В зависимости от версии Dify, раздел может находиться в разных местах:
   
   **Вариант A: В настройках приложения (Application API Key)**
   - Перейдите в раздел **"Studio"** или **"Apps"**
   - Выберите или создайте любое приложение
   - В настройках приложения найдите раздел **"API Keys"** или **"API Access"**
   - Создайте новый API ключ с правами **"Dataset Operator"** или **"Admin"**
   
   **Вариант B: В настройках Workspace**
   - В правом верхнем углу нажмите на иконку профиля/настройки
   - Выберите **"Settings"** или **"Workspace Settings"**
   - Найдите раздел **"API Keys"** или **"API Access"**
   - Создайте новый ключ с правами **"Dataset Operator"** или **"Admin"**
   
   **Вариант C: В разделе Knowledge Base**
   - Перейдите в раздел **"Knowledge Base"** или **"Datasets"**
   - Найдите настройки или раздел **"API Keys"**
   - Создайте ключ для управления датасетами

3. **Создайте API ключ:**
   - Нажмите **"Create API Key"**, **"Add API Key"** или **"Create New Secret Key"**
   - Укажите имя ключа (например, "Worker Admin Key")
   - Выберите права доступа: **"Dataset Operator"** или **"Admin"**
   - Подтвердите создание

4. **Скопируйте ключ:**
   - После создания ключ будет показан **один раз**
   - Скопируйте его полностью (формат обычно: `app-...` или `dataset-...`)
   - **Важно:** Сохраните ключ сразу, так как его нельзя будет посмотреть позже

5. **Добавьте ключ в `.env`:**
   ```bash
   DIFY_KEY_ADMIN=ваш-скопированный-ключ
   ```

**Проверка ключа:**

После добавления ключа в `.env`, проверьте его работоспособность:

```bash
curl -H "Authorization: Bearer ваш-ключ" http://localhost:5001/v1/datasets
```

Если ключ валидный, вы получите список датасетов (может быть пустым). Если получите `401 Unauthorized`, ключ неверный или не имеет нужных прав.

**Важно:**
- `DIFY_KEY_ADMIN` должен иметь права **Dataset Operator** или **Admin**
- Ключ должен работать с эндпоинтами `/datasets/*` (не только с `/workflows/run`)
- Если не можете найти раздел API Keys, проверьте документацию вашей версии Dify: https://docs.dify.ai

## Очереди и Задачи (API Reference)

### Очередь быстрых задач (Fast Lane: `ai-interactive-queue`)

#### `CMD_GEN_RESPONSE` — Генерация ответа (External RAG)

**Вход:**
```json
{
  "orgId": "123",
  "query": "Как сбросить пароль?",
  "history": [
    { "role": "user", "content": "Здравствуйте" },
    { "role": "assistant", "content": "Здравствуйте! Чем могу помочь?" }
  ],
  "meta": {
    "ticketId": "555",
    "user": "user-123"
  }
}
```

**Логика:**
1. Получение ID баз знаний (`adminKbId`, `historyKbId`) из Redis по `orgId`
2. Параллельный поиск чанков из обеих баз через Dify API (`retrieveChunks`)
3. Сборка контекста из найденных чанков
4. Обрезка истории, если она превышает лимит модели
5. Генерация ответа через Dify Workflow с собранным контекстом
6. Извлечение usage (токенов) из ответа

**Выход:**
```json
{
  "status": "success",
  "data": {
    "text": "Для сброса пароля...",
    "sources": [...],
    "usage": {
      "promptTokens": 1000,
      "completionTokens": 500,
      "totalTokens": 1500,
      "model": "gpt-4"
    }
  },
  "meta": { "ticketId": "555", "user": "user-123" }
}
```

## Troubleshooting

### Ошибка `KB_NOT_FOUND`

**Проблема:** Воркер не может найти базу знаний для организации.

**Решение:**
1. Проверьте, что `DIFY_KEY_ADMIN` настроен и имеет права Dataset Operator или Admin
2. Выполните синхронизацию кэша:
   ```json
   {
     "name": "CMD_SYS_RESYNC_CACHE",
     "data": { "meta": {} }
   }
   ```
3. Убедитесь, что база знаний существует в Dify для данной организации

### Сброс кэша

Для полной синхронизации кэша Redis с состоянием Dify используйте задачу `CMD_SYS_RESYNC_CACHE`:

```json
{
  "name": "CMD_SYS_RESYNC_CACHE",
  "data": { "meta": {} }
}
```

Эта задача:
- Получает список всех датасетов из Dify
- Синхронизирует Redis кэш с актуальным состоянием
- Возвращает статистику синхронизации

### Проблемы с подключением к Redis

**Проблема:** Воркер не может подключиться к Redis.

**Решение:**
1. Проверьте `REDIS_HOST` и `REDIS_PORT` в `.env`
2. Убедитесь, что Redis запущен: `docker-compose ps redis`
3. Проверьте пароль: `REDIS_PASSWORD` должен быть установлен в production

### Проблемы с Dify API

**Проблема:** Ошибки при вызове Dify API.

**Решение:**
1. Проверьте `DIFY_API_URL` (должен заканчиваться на `/v1`)
2. Убедитесь, что все ключи (`DIFY_KEY_ADMIN`, `DIFY_KEY_CLASSIFIER`, и т.д.) настроены
3. Проверьте доступность Dify API: `curl http://localhost:5001/v1/datasets`
