# Техническое задание: Slow Lane Worker - Этап 3: Интеграция в воркер (CMD_KB_ADD_FILE)

**Контекст:** Загрузка файлов в `about/9.md` критична из-за потоков и таймаутов. На третьем этапе интегрируется полный цикл загрузки файла: Lazy Loading -> скачивание -> загрузка в Dify с учетом Rate Limiter для предотвращения перегрузки Dify.

**Цель:** Реализовать обработчик `CMD_KB_ADD_FILE` в `src/workers/slowLaneWorker.js`, который соединяет скачивание файла через `FileService.downloadStream` и загрузку в Dify через `difyApi.uploadFile` с учетом Rate Limiter и обработки ошибок.

## 1. Задачи реализации

### 1.1 Реализовать обработчик `CMD_KB_ADD_FILE`

**Назначение:** Обработать задачу загрузки файла в базу знаний организации.

**Входные данные:**

```javascript
{
  orgId: string,        // ID организации
  fileUrl: string,      // URL файла для скачивания (например, из S3)
  fileName: string,     // Имя файла (будет использовано в Dify)
  meta: object          // Метаданные (опционально)
}
```

**Алгоритм:**

1.  **Lazy Init (Гарантия существования базы):**
    
    -   Вызвать `OrganizationService.ensureAdminKb(orgId)` для гарантии существования базы знаний для файлов.
        
    -   Сервис вернет `adminKbId` (datasetId). Внутри он использует Admin Key (см. `about/7.md`).
        
    -   **Обработка ошибок:** Если база не может быть создана, залогировать ошибку и вернуть error payload в `resultQueue`.
        
2.  **Скачивание файла:**
    
    -   Использовать метод `FileService.downloadStream(fileUrl)` для скачивания файла.
        
    -   Получить объект `{ stream, size }` (ReadStream и размер файла в байтах).
        
    -   **Важно:** Размер файла (`size`) будет использован при загрузке в Dify для указания `knownLength` в `form-data`, что предотвратит проблемы с chunked-кодированием.
        
    -   **Обработка ошибок:** Если скачивание не удалось (404, таймаут, idle timeout), залогировать ошибку и вернуть error payload в `resultQueue`.
        
3.  **Загрузка в Dify:**
    
    -   **Ключ:** Использовать **`config.dify.keys.admin`** для авторизации.
        
    -   Вызов: `difyApi.uploadFile(adminKey, adminKbId, stream, fileName, 'system', size)`.
        
    -   **Критично:**
        
        -   Передать в метод `uploadFile` именно `fileName` из задачи, а не имя из URL.
            
        -   Передать размер файла (`size`) в качестве последнего параметра, чтобы `form-data` использовал `knownLength` вместо chunked-кодирования.
            
    -   **Обработка ошибок:** Если загрузка не удалась, залогировать ошибку и вернуть error payload в `resultQueue`. При ошибках отсутствия ресурса (404, `dataset_not_found`) вызвать `ErrorHandler.handleDifyResourceError` для инвалидации кэша.
        
4.  **Статус:**
    
    -   Вернуть статус, который отдал Dify (обычно `indexing` или ID документа).

**Результат:**

```javascript
{
  success: true,
  data: {
    fileId: '...',        // ID документа в Dify
    status: 'indexing',  // Статус индексации
    fileName: '...',     // Имя файла
    orgId: '...'         // ID организации
  }
}
```

**Зависимости:**

-   `OrganizationService` (метод `ensureAdminKb`, должен быть реализован в `about/7.md` или `7_3.md`).
    
-   `FileService` (метод `downloadStream`, должен быть реализован в `9_1.md`).
    
-   `difyApi` (метод `uploadFile`, должен быть доработан в `9_2.md`).
    
-   `ErrorHandler` (для нормализации ошибок и инвалидации кэша, `about/10.md`).
    
-   `resultQueue` (очередь результатов, `about/6.md`).
    
-   Конфигурация (`config.dify.keys.admin`).
    
-   Логгер.

### 1.2 Интеграция Rate Limiter

**Назначение:** Ограничить частоту обработки задач `CMD_KB_ADD_FILE` для предотвращения перегрузки Dify.

**Требования (из `about/9.md`, раздел 1):**

-   **Для задач `CMD_KB_ADD_FILE`:**
    
    -   `max`: **1** (максимум 1 задача).
        
    -   `duration`: **1000-2000** (в 1-2 секунды).
        
    -   **Критично:** 10 файлов в секунду — это эквивалентно DDoS-атаке на Dify. Процесс индексации документов очень ресурсоемкий.
        
-   **Конфигурация:** Настройки Rate Limiter должны быть настраиваемыми через конфиг (например, `config.workers.slowLane.rateLimiter.fileUpload`).

**Реализация:**

-   Rate Limiter настраивается в фабрике воркеров (`bullmq/factory.js`) при создании воркера Slow Lane.
    
-   Для задач `CMD_KB_ADD_FILE` применяется отдельный Rate Limiter с жесткими ограничениями.
    
-   Если BullMQ не поддерживает разные Rate Limiter для разных типов задач в одной очереди, можно использовать отдельные очереди или жестко ограничить `concurrency: 2` для всего воркера.

**Зависимости:**

-   BullMQ инфраструктура (`about/6.md`).
    
-   Конфигурация (`config.workers.slowLane.rateLimiter.fileUpload`).

### 1.3 Обработка ошибок

**Назначение:** Корректно обработать все типы ошибок и отправить error payload в `resultQueue`.

**Алгоритм:**

1.  **Использовать `ErrorHandler` для нормализации ошибок:**
    
    -   Вызвать `ErrorHandler.normalizeError(error)` для стандартизации формата ошибки.
        
    -   Создать error payload через `ErrorHandler.createErrorPayload(error, jobId, orgId)`.
        
2.  **Применить стратегию инвалидации кэша:**
    
    -   Вызвать `ErrorHandler.handleDifyResourceError(error, orgId)` перед созданием error payload.
        
    -   Метод автоматически проверит, является ли ошибка ошибкой отсутствия ресурса (например, `dataset_not_found`, 404 статус).
        
    -   Если ошибка связана с отсутствием ресурса, метод вызовет `OrganizationService.invalidateOrgCache(orgId)` для инвалидации кэша.
        
3.  **Отправить ошибку в resultQueue:**
    
    -   Отправить error payload в `resultQueue` с корректным форматом.
        
    -   Выбросить ошибку (`throw err`), чтобы BullMQ пометил джоб как Failed и применил стратегию Retry с экспоненциальной задержкой (см. `about/6.md`, раздел "Стратегия Retry (Backoff)").

**Зависимости:**

-   `ErrorHandler` (`about/10.md`).

## 2. Структура файла

**Файл:** `src/workers/slowLaneWorker.js`

**Импорты:**

```javascript
const config = require('../config');
const logger = require('../utils/logger');
const difyApi = require('../infrastructure/dify/api');
const OrganizationService = require('../services/OrganizationService');
const FileService = require('../services/FileService');
const ErrorHandler = require('../utils/errorHandler');
const resultQueue = require('../infrastructure/bullmq/resultQueue');
```

**Обработчик:**

```javascript
async function handleKbAddFile(job) {
  const { orgId, fileUrl, fileName, meta } = job.data;
  const adminKey = config.dify.keys.admin;
  
  try {
    // Шаг 1: Lazy Init
    const adminKbId = await OrganizationService.ensureAdminKb(orgId);
    logger.info(`Admin KB ensured for org ${orgId}: ${adminKbId}`);
    
    // Шаг 2: Скачивание файла
    const { stream, size } = await FileService.downloadStream(fileUrl);
    logger.info(`File downloaded: ${fileName}, size: ${size} bytes`);
    
    // Шаг 3: Загрузка в Dify
    const result = await difyApi.uploadFile(
      adminKey,
      adminKbId,
      stream,
      fileName,  // Использовать fileName из задачи, а не из URL
      'system',
      size       // Передать размер для knownLength в form-data
    );
    
    logger.info(`File uploaded to Dify: ${fileName}, result:`, result);
    
    // Вернуть результат
    return {
      success: true,
      data: {
        fileId: result.document_id || result.id,
        status: result.status || 'indexing',
        fileName,
        orgId
      }
    };
  } catch (error) {
    logger.error(`Error in CMD_KB_ADD_FILE for org ${orgId}:`, error);
    
    // Обработка ошибок
    await ErrorHandler.handleDifyResourceError(error, orgId);
    const errorPayload = ErrorHandler.createErrorPayload(error, job.id, orgId);
    await resultQueue.add('result', errorPayload);
    
    throw error; // Для BullMQ retry
  }
}
```
