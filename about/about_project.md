

# Техническое задание на разработку микросервиса Ticket-AI-Worker

## 1\. Общие сведения

**Наименование:** Ticket AI Worker Service

**Цель:** Создание асинхронного микросервиса для обработки NLP-задач (генерация текста, классификация, RAG-поиск) с использованием платформы Dify.

**Принцип работы:** Микросервис не имеет внешнего HTTP API для клиентов. Взаимодействие с основным приложением (Main App) происходит строго через очереди сообщений (Redis/BullMQ).

## 2\. Архитектура и Стек

### 2.1 Технологический стек

-   **Язык:** Node.js (последняя LTS версия).
    
-   **Очереди:** BullMQ (Redis).
    
-   **AI Engine:** Dify (Self-hosted Docker версия).
    
-   **Хранилище состояний (Кэш):** Redis. Используется для хранения маппинга `OrgID` -> `Dify Dataset IDs`.
    
    -   **Стратегия хранения:** Redis выступает как постоянное хранилище "горячих" данных.
        
    -   **Cache Warming:** При запуске сервис синхронизирует список датасетов из Dify.
        
    -   **Источник истины:** Платформа Dify (Naming Convention).
        
-   **Паттерн RAG:** **External RAG**.
    
    -   Воркер **сам** выполняет поиск (Retrieval) через API Dify, используя Admin Key.
        
    -   Воркер формирует текстовый контекст.
        
    -   Dify Workflow используется только как LLM-движок для генерации финального ответа.
        

### 2.2 Схема потоков данных

1.  **`ai-interactive-queue` (Fast Lane)**
    
    -   Чат, перевод, анализ, **RAG-генерация**.
        
    -   Высокий `concurrency`, многопоточность.
        
2.  **`ai-background-queue` (Slow Lane)**
    
    -   Загрузка файлов, архивация, системная синхронизация.
        
    -   Низкий `concurrency`, Rate Limiter.
        
3.  **`ai-results-queue` (Output)**
    
    -   Единый канал для возврата результатов.
        

## 3\. Модули и задачи микросервиса (Tasks)

### 3.1 Общие требования к данным

-   **Поле `meta`:** Context Pass-through.
    
-   **Форматирование:** Markdown.
    

### 3.2 Очередь быстрых задач (Fast Lane: `ai-interactive-queue`)

#### Задача: Классификация и Анализ (`CMD_ANALYZE_NEW_TICKET`)

-   **Вход:** `{ "action": "...", "text": "...", "targetLanguage": "ru", "meta": {...} }`
    
-   **Логика:**
    
    -   Вызов Dify Workflow "Classifier" (App Key).
        
    -   Парсинг JSON-ответа (`title`, `sentiment`).
        

#### Задача: Генерация ответа RAG (`CMD_GEN_RESPONSE`) — **External RAG**

-   **Вход:**
    
    JSON
    
        {
          "action": "CMD_GEN_RESPONSE",
          "orgId": "123",
          "query": "Вопрос...",
          "history": "История...",
          "meta": { "ticketId": "555" }
        }
    
-   **Логика:**
    
    1.  **Dataset Identification:** Получить ID баз (`adminKbId`, `historyKbId`) из Redis по `orgId`.
        
    2.  **Strict Check:** Если баз нет в Redis — вернуть ошибку `KB_NOT_FOUND`.
        
    3.  **Retrieval (Parallel):**
        
        -   Использовать ключ **`DIFY_KEY_ADMIN`**.
            
        -   Вызвать поиск (`retrieveChunks`) параллельно для обеих баз.
            
        -   Собрать релевантные куски текста.
            
    4.  **Context Assembly:** Объединить куски в одну строку `context`.
        
    5.  **Generation:**
        
        -   Вызвать Dify Workflow "Support Helper" (App Key).
            
        -   Передать переменные: `query`, `history`, **`context`**.
            
-   **Выход:** Успех (текст + sources) или Ошибка.
    

#### Задача: Перевод текста (`CMD_TRANSLATE`)

-   **Логика:** Простой вызов LLM через Dify.
    

#### Задача: Получение списка файлов (`CMD_KB_LIST_FILES`)

-   **Логика:** Использовать **`DIFY_KEY_ADMIN`** и ID базы из Redis для получения списка документов.
    

#### Задача: Удаление файла (`CMD_KB_DELETE_FILE`)

-   **Логика:** Использовать **`DIFY_KEY_ADMIN`** для удаления документа.
    

### 3.3 Очередь фоновых задач (Slow Lane: `ai-background-queue`)

#### Задача: Загрузка нового файла (`CMD_KB_ADD_FILE`)

-   **Вход:** `{ "orgId": "...", "fileUrl": "...", "fileName": "..." }`
    
-   **Логика:**
    
    1.  **Lazy Init:** Если базы нет, создать её (используя **`DIFY_KEY_ADMIN`**).
        
    2.  **Скачивание:** Stream файла из S3.
        
    3.  **Загрузка:** Отправка в Dify с указанием `fileName` (используя **`DIFY_KEY_ADMIN`**).
        

#### Задача: Архивация тикета (`CMD_ARCHIVE_TICKET`)

-   **Логика:**
    
    1.  **Суммаризация:** Вызов Workflow "Summarizer" (App Key).
        
    2.  **Индексация:** Сохранение результата в базу истории через **`DIFY_KEY_ADMIN`**.
        

#### Задача: Принудительная синхронизация кэша (`CMD_SYS_RESYNC_CACHE`)

-   **Логика:**
    
    1.  Получить список всех датасетов через **`DIFY_KEY_ADMIN`**.
        
    2.  Обновить Redis.
        

## 4\. Конфигурация Dify (Требования к настройке)

Необходимо создать 3 приложения и иметь 1 Admin Key.

1.  **Global:**
    
    -   **Admin Key:** API-ключ с правами `Dataset Operator` (или Admin) для управления базами и поиска.
        
2.  **App 1: Ticket Classifier (Workflow)**
    
    -   _Input:_ `message`.
        
    -   _Output:_ JSON `{title, sentiment}`.
        
    -   **Системный промпт в узле LLM:**
        
        -   Workflow в Dify — это "глупая" цепочка узлов. LLM не понимает контекст автоматически, поэтому системный промпт должен явно указывать, как обрабатывать входные данные.
            
        -   **Пример системного промпта:**
            
            Markdown
            
                Ты — система классификации тикетов техподдержки.
                
                Проанализируй следующее сообщение пользователя и верни JSON с двумя полями:
                - title: краткое название проблемы (до 50 символов)
                - sentiment: эмоциональная окраска ("positive", "neutral", "negative")
                
                Сообщение пользователя: {{message}}
                
                Верни только валидный JSON, без дополнительного текста.
        
3.  **App 2: Ticket Summarizer (Workflow)**
    
    -   _Input:_ `ticket_history`.
        
    -   _Output:_ Markdown summary.
        
    -   **Системный промпт в узле LLM:**
        
        -   **Критично:** Переменная `ticket_history` содержит структурированный диалог с префиксами `User:` и `Assistant:`. Промпт должен явно указать LLM, что это история переписки, и как её использовать.
            
        -   **Пример системного промпта:**
            
            Markdown
            
                Ты — система суммаризации тикетов техподдержки.
                
                Ниже представлена история переписки между пользователем и оператором техподдержки.
                Каждая реплика помечена префиксом "User:" (пользователь) или "Assistant:" (оператор).
                
                История переписки:
                {{ticket_history}}
                
                Задача: Создай краткую сводку тикета в формате Markdown, включающую:
                1. Описание проблемы пользователя
                2. Предложенное решение
                3. Итоговый статус (решена/не решена)
                
                Используй информацию из истории переписки для составления сводки.
        
4.  **App 3: Support Helper (Workflow)**
    
    -   _Тип:_ **Workflow** (Stateless).
        
    -   _Input Variables:_ `query`, `history`, **`context`**.
        
    -   **Системный промпт в узле LLM:**
        
        -   **Критично:** Workflow в Dify — это "глупая" цепочка. Если просто передать переменные `history` и `context` без явного указания в промпте, LLM не поймет, что это диалог и контекст для ответа. Без правильной связки в промпте передача истории и контекста бесполезна.
            
        -   **Пример системного промпта:**
            
            Markdown
            
                Ты — оператор техподдержки. Твоя задача — помочь пользователю решить его проблему.
                
                **История переписки:**
                Ниже представлена история текущего тикета. Каждая реплика помечена префиксом "User:" (пользователь) или "Assistant:" (оператор).
                
                {{history}}
                
                **Контекст из базы знаний:**
                Ниже представлена релевантная информация из базы знаний, которая может помочь ответить на вопрос пользователя.
                
                {{context}}
                
                **Текущий вопрос пользователя:**
                {{query}}
                
                **Инструкции:**
                1. Используй историю переписки, чтобы понять контекст проблемы
                2. Используй контекст из базы знаний для предоставления точной информации
                3. Ответь на текущий вопрос пользователя, учитывая всю доступную информацию
                4. Если в истории уже обсуждалась эта тема, сделай ссылку на предыдущие реплики
                5. Ответ должен быть полезным, точным и дружелюбным
                
                Ответь на вопрос пользователя:
        
    -   _Структура графа:_
        
        1.  **Start**
            
        2.  **LLM**: Узел с системным промптом (см. выше) и переменными `{{query}}`, `{{history}}`, `{{context}}`.
            
        3.  **End**
            
    -   _Важно:_ 
        
        -   **Узел "Knowledge Retrieval" НЕ используется внутри графа.** Поиск выполняется воркером через External RAG, а в Workflow передается уже готовый контекст.
            
        -   **Промпт-инжиниринг критичен:** Без явного указания в системном промпте, что `history` — это история диалога, а `context` — это контекст из базы знаний, LLM не сможет корректно использовать эти данные для генерации ответа.
            

## 5\. Обработка ошибок и Мониторинг

-   **Dify Unavailable:** Retry (Backoff).
    
-   **Billing:** Извлекать `usage` из ответов Workflow.
    

## 6\. Деплоймент

-   **Docker:** `node:lts-alpine` + системные зависимости.
    
-   **Переменные окружения:**
    
    -   **Redis:**
        
        -   `REDIS_HOST`, `REDIS_PORT`
            
        -   **`REDIS_PASSWORD`** (Обязательно для Prod)
            
    -   **Dify API:**
        
        -   `DIFY_API_URL`
            
        -   **`DIFY_KEY_ADMIN`** (Новый ключ)
            
        -   `DIFY_KEY_CLASSIFIER`
            
        -   `DIFY_KEY_SUMMARIZER`
            
        -   `DIFY_KEY_RESPONSE_WORKFLOW`
            
    -   **Workers (BullMQ):**
        
        -   `WORKER_FAST_LANE_CONCURRENCY` (опционально, по умолчанию `15`). Количество одновременных задач для Fast Lane воркера. Позволяет тюнить производительность без пересборки контейнера.
            
        -   `WORKER_SLOW_LANE_CONCURRENCY` (опционально, по умолчанию `2`). Количество одновременных задач для Slow Lane воркера. Позволяет тюнить производительность без пересборки контейнера.
            
        -   **Важно:** Эти настройки не должны хардкодиться в `index.js` или других файлах. Они должны читаться из `.env` через модуль конфигурации (`config.workers.fastLane.concurrency`, `config.workers.slowLane.concurrency`).
            
    -   **Healthcheck:**
        
        -   `HEALTHCHECK_PORT` (опционально, по умолчанию `3000`). Порт для HTTP-сервера healthcheck эндпоинта. Используется для проверки работоспособности сервиса в Docker Compose и оркестраторах (Kubernetes).
