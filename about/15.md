

# Техническое задание: Воркер Медленной Очереди (Slow Lane)

**Контекст:** Быстрые задачи обрабатываются отдельно. Теперь необходимо реализовать обработку фоновых задач в очереди `ai-background-queue`. Эти задачи связаны с тяжелыми операциями ввода-вывода (загрузка файлов) и генерацией контента (суммаризация), поэтому воркер должен работать в щадящем режиме.

**Цель:** Реализовать файл `src/workers/slowLaneWorker.js` и соответствующие обработчики задач. Обеспечить корректное взаимодействие с `OrganizationService` и использование **Admin Key** для операций с датасетами.

## 1\. Конфигурация Воркера

В отличие от Fast Lane, здесь критически важны настройки ограничения нагрузки.

**Требования к фабрике (bullmq/factory.js):** Воркер должен быть инициализирован со следующими параметрами:

-   **Concurrency:** 2 (жесткое ограничение для предотвращения перегрузки Dify).
    
    -   **Важно:** Для задач загрузки файлов (`CMD_KB_ADD_FILE`) процесс индексации документов (Embedding Generation) очень ресурсоемкий. Даже при `concurrency: 5` одновременная обработка нескольких больших файлов (например, PDF по 50 МБ) может привести к перегрузке self-hosted инсталляции Dify (Vector DB + API) и падению по OOM (Out Of Memory) или таймауту.
        
    -   **Рекомендация:** Установить `concurrency: 2` для всего воркера Slow Lane, чтобы гарантировать, что не более 2 задач обрабатываются одновременно, независимо от типа задачи.
    
-   **Rate Limiter:**
    
    -   **Для задач `CMD_KB_ADD_FILE` (загрузка файлов):**
        
        -   `max`: **1** (максимум 1 задача).
            
        -   `duration`: **1000-2000** (в 1-2 секунды).
            
        -   **Критично:** 10 файлов в секунду — это эквивалентно DDoS-атаке на Dify. Процесс индексации документов требует:
            
            -   Загрузки файла в Dify API.
                
            -   Парсинга содержимого (PDF, DOCX и т.д.).
                
            -   Генерации эмбеддингов для каждого чанка (векторизация).
                
            -   Сохранения в векторную базу данных (Weaviate/Qdrant).
                
            -   Индексации в базе данных Dify (Postgres).
                
        -   **Риск перегрузки:** Если 10 пользователей одновременно отправят PDF по 50 МБ, self-hosted инсталляция Dify (Vector DB + API) скорее всего упадет по OOM или таймауту, даже при `concurrency: 5`.
            
        -   **Решение:** Жестко ограничить загрузку файлов до 1 файла в 1-2 секунды. Это обеспечит стабильность работы Dify даже при пиковых нагрузках.
            
    -   **Для других задач (`CMD_ARCHIVE_TICKET`, `CMD_SYS_RESYNC_CACHE`, `CMD_CLEANUP_ORG`):**
        
        -   Можно использовать более мягкие ограничения (например, `max: 5`, `duration: 1000`), так как эти задачи менее ресурсоемкие.
            
        -   Однако, учитывая общее ограничение `concurrency: 2`, они все равно не будут обрабатываться слишком часто.
            
        -   **Примечание:** Задача `CMD_CLEANUP_ORG` (очистка ресурсов организации) не требует жестких ограничений, так как выполняется редко (только при удалении организации) и не создает нагрузку на индексацию.
            
    -   **Конфигурация:** Настройки Rate Limiter должны быть настраиваемыми через конфиг (например, `config.workers.slowLane.rateLimiter.fileUpload` и `config.workers.slowLane.rateLimiter.other`), чтобы можно было изменять их без пересборки кода.
        
    -   **Альтернативный подход:** Если BullMQ не поддерживает разные Rate Limiter для разных типов задач в одной очереди, можно использовать отдельные очереди для загрузки файлов и других фоновых задач, либо жестко ограничить `concurrency: 2` для всего воркера, что автоматически ограничит частоту обработки всех задач.
        

## 2\. Структура Процессора

**Алгоритм:**

1.  **Импорт:** `config`, `logger`, `difyApi`, `OrganizationService`, утилиты (`historyFormatter`, `errorHandler`, `billingService`).
    
2.  **Логирование:** `logger.info('Processing slow job', { id: job.id, name: job.name })`.
    
3.  **Маршрутизация (Switch):**
    
    -   `CMD_KB_ADD_FILE`
        
    -   `CMD_ARCHIVE_TICKET`
        
    -   `CMD_SYS_RESYNC_CACHE`
        
    -   `CMD_CLEANUP_ORG`
        
4.  **Обработка:** Вызов хендлеров.
    
5.  **Отправка результата:** В `resultQueue`.
    
6.  **Обработка ошибок:** Стандартная (catch -> error payload -> throw).
    
    -   Выбросить ошибку (`throw err`), чтобы BullMQ пометил джоб как Failed и применил стратегию Retry с экспоненциальной задержкой (см. `about/6.md`, раздел "Стратегия Retry (Backoff)").
        
    -   **Важно:** Стратегия retry применяется автоматически для временных ошибок (сетевые ошибки, 502, 503, таймауты). Для постоянных ошибок (404, 401) задача будет помечена как Failed без повторных попыток.
    

## 3\. Реализация Обработчиков (Handlers)

### 3.1 Загрузка Файла (`CMD_KB_ADD_FILE`)

-   **Вход:** `orgId`, `fileUrl`, `fileName`, `meta`.
    
-   **Действия:**
    
    1.  **Lazy Init:** Вызов `OrganizationService.ensureAdminKb(orgId)`.
        
        -   Сервис вернет `datasetId`. (Внутри он использует Admin Key, см. `about/7.md`).
            
    2.  **Скачивание:**
        
        -   Использовать вспомогательный метод `FileService.downloadStream(fileUrl)`.
            
        -   Получить объект `{ stream, size }` (ReadStream и размер файла в байтах).
            
        -   **Важно:** Размер файла (`size`) будет использован при загрузке в Dify для указания `knownLength` в `form-data`, что предотвратит проблемы с chunked-кодированием.
            
    3.  **Загрузка в Dify:**
        
        -   **Ключ:** Использовать **`config.dify.keys.admin`**.
            
        -   Вызов: `difyApi.uploadFile(adminKey, datasetId, stream, fileName, 'system', size)`.
            
        -   _Критично:_ 
            
            -   Передать в метод `uploadFile` именно `fileName` из задачи, а не имя из URL.
                
            -   Передать размер файла (`size`) в качестве последнего параметра, чтобы `form-data` использовал `knownLength` вместо chunked-кодирования.
            
    4.  **Статус:** Вернуть статус, который отдал Dify (обычно `indexing` или ID документа).
        
-   **Результат:** `{ fileId: '...', status: 'indexing' }`.
    

### 3.2 Архивация Тикета (`CMD_ARCHIVE_TICKET`)

-   **Вход:** `orgId`, `fullTicketHistory` (массив сообщений или Markdown), `meta`.
    
    -   **Формат истории:** Поле `fullTicketHistory` должно быть передано в одном из двух форматов:
        
        1.  **Массив сообщений** (предпочтительно, рекомендуется для Main App):
            
            JavaScript
            
                [
                  { role: 'user', content: 'Здравствуйте, у меня проблема...' },
                  { role: 'assistant', content: 'Здравствуйте! Расскажите подробнее...' },
                  { role: 'user', content: 'Не могу войти в систему...' }
                ]
            
            -   **Рекомендация для Main App:** Передавать полную историю тикета именно в виде массива сообщений, а не в виде отформатированного Markdown. Это обеспечивает гибкость и позволяет воркеру контролировать форматирование перед суммаризацией.
                
        2.  **Строка Markdown** (альтернативный вариант, если Main App уже выполняет пре-форматирование):
            
            Markdown
            
                User: Здравствуйте, у меня проблема...
                
                Assistant: Здравствуйте! Расскажите подробнее...
                
                User: Не могу войти в систему...
            
            -   **Требования к формату:** Если Main App передает уже отформатированный Markdown, он должен строго следовать структуре с четким разделением реплик через префиксы `User:` и `Assistant:` (или `user:` и `assistant:`, регистр не важен).
                
            -   **Важно:** Если Main App передает "плоский" текст без структурирования, LLM может запутаться при суммаризации и некорректно интерпретировать, где реплика пользователя, а где оператора.
                
    -   **Важно:** LLM очень чувствительны к формату диалога. Для корректной суммаризации необходимо передать историю в структурированном формате с четким разделением реплик пользователя и оператора.
    
-   **Действия:**
    
    1.  **Lazy Init:** Вызов `OrganizationService.ensureHistoryKb(orgId)`. Получить `datasetId`.
        
    2.  **Форматирование истории:**
        
        -   Использовать утилиту `formatTicketHistory` из `src/utils/historyFormatter.js` для преобразования истории в структурированный Markdown.
            
        -   Если `fullTicketHistory` — массив, отформатировать его в строку с четким разделением реплик (`User:` / `Assistant:`).
            
        -   Если `fullTicketHistory` — строка, проверить формат и при необходимости отформатировать.
            
    3.  **Суммаризация:**
        
        -   **Ключ:** Использовать **`config.dify.keys.summarizer`**.
            
        -   Вызов: `difyApi.runWorkflow(summarizerKey, { ticket_history: formattedHistory })`.
            
            -   **Важно:** Передать отформатированную историю (`formattedHistory`), а не исходную `fullTicketHistory`, чтобы LLM корректно понимал структуру диалога.
                
        -   **Важно — Промпт-инжиниринг:**
            
            -   Workflow в Dify — это "глупая" цепочка узлов. LLM не понимает автоматически, что переменная `ticket_history` содержит структурированный диалог с префиксами `User:` и `Assistant:`.
                
            -   **Требование:** Системный промпт в узле LLM Workflow "Ticket Summarizer" должен явно указывать, что `{{ticket_history}}` — это история переписки с префиксами `User:` и `Assistant:`, и как использовать эту информацию для создания сводки.
                
            -   Без правильной связки в промпте передача истории бесполезна — LLM не сможет корректно интерпретировать структуру диалога.
                
            -   Подробные требования к системному промпту см. в `about_project.md`, раздел 4, "App 2: Ticket Summarizer (Workflow)".
                
        -   Получить результат (Markdown с описанием проблемы и решения).
            
    3.  **Индексация:**
        
        -   **Ключ:** Использовать **`config.dify.keys.admin`** (так как мы пишем в базу).
            
        -   Вызов: `difyApi.createDocumentByText(adminKey, datasetId, docName, summaryText)`.
            
        -   `docName` сформировать как `Ticket #{meta.ticketId}`.
            
-   **Результат:** `{ docId: '...', summary: '...' }`.

### 3.4 Очистка ресурсов организации (`CMD_CLEANUP_ORG`)

-   **Вход:** `orgId`, `meta`.
    
    -   **Контекст:** Задача вызывается при удалении организации в основном приложении (Main App). Необходимо физически удалить все связанные ресурсы в Dify и очистить кэш в Redis, чтобы предотвратить накопление "осиротевших" датасетов.
        
    -   **Проблема:** Если организация удаляется в Main App, но ресурсы не очищаются в микросервисе, в Dify останутся "осиротевшие" датасеты (`KB_ADMIN_{orgId}`, `KB_HISTORY_{orgId}`). Со временем это засорит векторную базу данных (Weaviate/Qdrant) и Redis, что приведет к:
        
        -   Накоплению неиспользуемых данных в векторной базе.
            
        -   Заполнению Redis неактуальными записями.
            
        -   Увеличению времени синхронизации при `CMD_SYS_RESYNC_CACHE`.
            
        -   Потенциальным проблемам с производительностью.
            
-   **Действия:**
    
    1.  **Получение ID датасетов:**
        
        -   Попытаться получить ID датасетов из Redis через `redisCache.getOrgDatasets(orgId)`.
            
        -   Если данных в Redis нет (организация уже была удалена или никогда не создавалась), попытаться найти датасеты в Dify по именам:
            
            -   `KB_ADMIN_{orgId}`
                
            -   `KB_HISTORY_{orgId}`
                
        -   **Важно:** Если датасеты не найдены ни в Redis, ни в Dify, это не ошибка — возможно, организация была создана, но никогда не использовала функциональность загрузки файлов или архивации. В этом случае просто вернуть успешный результат.
            
    2.  **Удаление датасетов в Dify:**
        
        -   **Ключ:** Использовать **`config.dify.keys.admin`** (так как удаление датасетов требует прав администратора).
            
        -   Для каждого найденного датасета:
            
            -   Вызвать `difyApi.deleteDataset(adminKey, datasetId)`.
                
            -   **Обработка ошибок:** Если датасет уже был удален или не существует (404), это не критическая ошибка — просто залогировать предупреждение и продолжить.
                
            -   Если возникла другая ошибка (например, нет прав доступа), залогировать ошибку, но продолжить удаление других датасетов (graceful degradation).
                
        -   **Логирование:** Логировать каждый удаленный датасет: `logger.info('Dataset deleted', { orgId, datasetId, datasetName })`.
            
    3.  **Очистка Redis:**
        
        -   Вызвать `redisCache.deleteOrgDatasets(orgId)` для удаления записи организации из кэша.
            
        -   **Важно:** Очистка Redis должна происходить даже если удаление датасетов в Dify не удалось (частичная очистка лучше, чем полное отсутствие очистки).
            
    4.  **Статистика:**
        
        -   Подсчитать количество удаленных датасетов.
            
        -   Подсчитать количество ошибок (если были).
            
-   **Результат:** `{ deletedDatasets: 2, errors: 0, orgId }`.
    
    -   Если датасеты не были найдены: `{ deletedDatasets: 0, errors: 0, orgId, message: 'No datasets found for organization' }`.
        
-   **Обработка ошибок:**
    
    -   Если произошла критическая ошибка (например, потеря соединения с Dify), залогировать ошибку и вернуть частичный результат с указанием количества успешно удаленных датасетов.
        
    -   Не выбрасывать ошибку, если некоторые датасеты не удалось удалить — лучше вернуть результат с информацией об ошибках, чтобы Main App могло принять решение о повторной попытке.
    

## 4\. Сервис Файлов (`src/services/FileService.js`)

Простая обертка для скачивания, чтобы не дублировать код axios в воркере.

**Методы:**

1.  **`downloadStream(url)`**:
    
    -   Использует `axios` (который уже есть в проекте).
        
    -   **Конфигурация запроса:**
        
        -   `method: 'GET'`
            
        -   `url`: URL файла для скачивания
            
        -   `responseType: 'stream'` — получение данных в виде потока
            
        -   **Таймауты:**
            
            1.  **Таймаут на подключение (`timeout`):**
                
                -   Установить таймаут на установление соединения и получение ответа (например, 30 секунд).
                    
                -   Если соединение не установилось в течение этого времени, axios выбросит ошибку `ETIMEDOUT`.
                    
            2.  **Таймаут на передачу данных (idle timeout):**
                
                -   **Проблема:** Если соединение с S3 (или другим источником файлов) зависнет (нет данных, но соединение открыто), воркер может висеть вечно, занимая слот `concurrency` и блокируя обработку других задач.
                    
                -   **Решение:** Установить таймаут на отсутствие данных в стриме (idle timeout). Если в течение определенного времени (например, 60 секунд) не приходят новые данные, стрим должен быть прерван с ошибкой.
                    
                -   **Реализация:** Использовать таймер на события стрима:
                    
                    JavaScript
                    
                        const stream = response.data;
                        let lastDataTime = Date.now();
                        const IDLE_TIMEOUT = 60000; // 60 секунд
                        
                        stream.on('data', () => {
                          lastDataTime = Date.now();
                        });
                        
                        const idleTimer = setInterval(() => {
                          if (Date.now() - lastDataTime > IDLE_TIMEOUT) {
                            stream.destroy(new Error('Stream idle timeout'));
                            clearInterval(idleTimer);
                          }
                        }, 5000); // Проверка каждые 5 секунд
                        
                        stream.on('end', () => clearInterval(idleTimer));
                        stream.on('error', () => clearInterval(idleTimer));
                    
                -   **Важно:** Таймаут должен быть настраиваемым через конфиг (например, `config.fileService.idleTimeout`), чтобы можно было изменять его в зависимости от размера файлов и скорости сети.
                    
    -   **Важно:** Получить заголовок `content-length` из ответа (`response.headers['content-length']`) и вернуть его вместе с потоком.
        
    -   **Возвращаемое значение:** Объект `{ stream: response.data, size: contentLength }`, где:
        
        -   `stream` — поток данных (ReadStream) с настроенными таймаутами.
            
        -   `size` — размер файла в байтах (число) или `null`, если заголовок `content-length` отсутствует.
            
    -   **Обработка ошибок:**
        
        -   Обрабатывать ошибки подключения (404, ETIMEDOUT) и выбрасывать понятные исключения.
            
        -   Обрабатывать ошибки idle timeout и выбрасывать исключение с понятным сообщением (например, `StreamTimeoutError: 'No data received for 60 seconds'`).
            
        -   **Важно:** При любой ошибке (включая таймауты) стрим должен быть корректно закрыт (`stream.destroy()`), чтобы освободить ресурсы и не оставлять "висячие" соединения.
            
    -   **Примечание:** Размер файла необходим для корректной загрузки в Dify через `form-data` с указанием `knownLength`, что предотвращает использование `Transfer-Encoding: chunked` и возможные проблемы с некоторыми серверами или прокси (например, Nginx перед Dify).

# Acceptance Criteria (Критерии приемки)

1.  \[ \] **Rate Limiting для загрузки файлов:** Задачи `CMD_KB_ADD_FILE` обрабатываются не чаще 1 раза в 1-2 секунды (или согласно конфигу). Это критически важно для предотвращения перегрузки Dify при индексации больших файлов.
    
2.  \[ \] **Concurrency для Slow Lane:** Воркер Slow Lane имеет жесткое ограничение `concurrency: 2`, что гарантирует, что не более 2 задач обрабатываются одновременно, независимо от типа задачи.
    
3.  \[ \] **DDoS Protection:** Настройки Rate Limiter предотвращают ситуацию, когда одновременная загрузка нескольких больших файлов (например, 10 PDF по 50 МБ) приводит к перегрузке Dify и падению по OOM или таймауту.
    
4.  \[ \] **Admin Key Usage:** Операции загрузки (`uploadFile`) и создания документов (`createDocumentByText`) используют `config.dify.keys.admin`.
    
5.  \[ \] **Lazy Loading:** При отправке файла для новой организации воркер корректно инициирует создание базы.
    
6.  \[ \] **File Naming:** В Dify файл появляется с корректным именем (из поля `fileName`).
    
7.  \[ \] **Summarization Flow:** Используются разные ключи: `summarizer` для LLM и `admin` для записи в базу.
    
8.  \[ \] **Axios Limits:** В клиенте Axios установлены `maxBodyLength: Infinity` и `maxContentLength: Infinity` для поддержки загрузки больших файлов (более 10-15 МБ).
    
9.  \[ \] **Content-Length Extraction:** Метод `FileService.downloadStream` корректно извлекает заголовок `content-length` из ответа и возвращает размер файла вместе с потоком.
    
10. \[ \] **Connection Timeout:** Метод `downloadStream` устанавливает таймаут на подключение (например, 30 секунд), предотвращая бесконечное ожидание установления соединения.
    
11. \[ \] **Idle Timeout:** Метод `downloadStream` устанавливает таймаут на отсутствие данных в стриме (idle timeout, например, 60 секунд), предотвращая зависание воркера при "зависших" соединениях с S3 или другими источниками файлов.
    
12. \[ \] **Stream Cleanup:** При любой ошибке (включая таймауты) стрим корректно закрывается (`stream.destroy()`), освобождая ресурсы и предотвращая "висячие" соединения, которые могут занимать слоты `concurrency`.
    
13. \[ \] **Timeout Configuration:** Таймауты (connection timeout и idle timeout) настраиваются через конфиг (например, `config.fileService.connectionTimeout` и `config.fileService.idleTimeout`), что позволяет изменять их без пересборки кода.
    
14. \[ \] **Form-Data knownLength:** Метод `difyApi.uploadFile` использует параметр `fileSize` для указания `knownLength` в `form-data`, что предотвращает использование `Transfer-Encoding: chunked` и проблемы с некоторыми серверами или прокси.
    
15. \[ \] **Large File Upload:** Загрузка больших файлов (например, PDF размером 50 МБ) проходит успешно без ошибок превышения лимита Axios или проблем с chunked-кодированием.
    
16. \[ \] **History Formatting:** Обработчик `CMD_ARCHIVE_TICKET` использует утилиту `formatTicketHistory` для преобразования истории тикета в структурированный Markdown формат перед передачей в Dify Workflow для суммаризации.
    
17. \[ \] **History Input Handling:** Обработчик корректно обрабатывает оба формата истории (массив сообщений и строку Markdown) и форматирует их перед суммаризацией.
    
18. \[ \] **Summarization Quality:** Отформатированная история обеспечивает корректное понимание LLM структуры диалога, что улучшает качество суммаризации и предотвращает путаницу между репликами пользователя и оператора.
    
19. \[ \] **Main App Format:** Main App передает полную историю тикета в виде массива сообщений (предпочтительно) или в виде структурированного Markdown с префиксами `User:` / `Assistant:`. Воркер корректно обрабатывает оба формата перед суммаризацией.
    
20. \[ \] **Format Validation:** Если Main App передает историю в виде строки, воркер проверяет наличие структурированного формата (префиксы `User:` / `Assistant:`) и логирует предупреждение при обнаружении "плоского" текста, который может ухудшить качество суммаризации.
    
21. \[ \] **Summarizer Prompt Engineering:** Системный промпт в узле LLM Workflow "Ticket Summarizer" явно указывает, что `{{ticket_history}}` — это история переписки с префиксами `User:` и `Assistant:`, и как использовать эту информацию для создания сводки. Без правильной связки в промпте передача истории неэффективна.
    
22. \[ \] **Rate Limiter Configuration:** Настройки Rate Limiter настраиваются через конфиг (например, `config.workers.slowLane.rateLimiter.fileUpload`), что позволяет изменять их без пересборки кода.
    
23. \[ \] **Stability Under Load:** При одновременной загрузке нескольких больших файлов (например, 5-10 PDF по 50 МБ) система остается стабильной, не происходит перегрузки Dify, падений по OOM или таймаутам благодаря жестким ограничениям Rate Limiter и Concurrency.
    
24. \[ \] **Organization Cleanup:** Обработчик `CMD_CLEANUP_ORG` корректно удаляет датасеты организации в Dify через Admin Key и очищает кэш в Redis при удалении организации в Main App.
    
25. \[ \] **Dataset Deletion:** Метод `difyApi.deleteDataset` корректно удаляет датасеты в Dify и обрабатывает случаи, когда датасет уже был удален или не существует (404), без выброса критических ошибок.
    
26. \[ \] **Graceful Cleanup:** При очистке ресурсов организации обработчик продолжает работу даже если некоторые датасеты не удалось удалить, возвращая частичный результат с информацией об успешно удаленных датасетах и ошибках.
    
27. \[ \] **Redis Cleanup:** Очистка Redis происходит даже если удаление датасетов в Dify не удалось, обеспечивая частичную очистку ресурсов.
    
28. \[ \] **Orphaned Datasets Prevention:** Регулярное использование `CMD_CLEANUP_ORG` при удалении организаций предотвращает накопление "осиротевших" датасетов в Dify и засорение векторной базы данных и Redis.
