# Техническое задание: Клиент Redis и Слой Кэширования

**Контекст:** Микросервис использует Redis для двух целей: как брокер очередей (BullMQ) и как хранилище "горячих" данных (маппинг `OrgID` -> `Dify Dataset IDs`). Нам необходимо создать надежный слой инфраструктуры для работы с Redis, который будет безопасно управлять соединением (включая аутентификацию) и предоставлять типизированные методы для работы с бизнес-данными.

**Цель:** Реализовать модуль `src/infrastructure/redis` с использованием библиотеки `ioredis`. Реализовать Singleton-подключение с поддержкой пароля и репозиторий для кэширования настроек организаций.

## 1\. Установка зависимостей

-   `ioredis`: Стандарт де-факто для работы с Redis в Node.js.
    

## 2\. Модуль подключения (`src/infrastructure/redis/client.js`)

Необходимо создать файл, отвечающий за низкоуровневое соединение.

**Требования:**

1.  **Singleton:** Модуль должен экспортировать единственный экземпляр подключения (или функцию для его получения).
    
2.  **Конфигурация:** Использовать настройки из `src/config`:
    
    -   `host`: `config.redis.host`
        
    -   `port`: `config.redis.port`
        
    -   `password`: `config.redis.password` (если задан)
        
3.  **Назначение клиента:**
    
    -   Этот клиент предназначен **только для бизнес-кэширования** (хранение маппинга `OrgID` -> `Dataset IDs` и других бизнес-данных).
        
    -   **Важно:** Этот клиент **НЕ должен использоваться** для BullMQ воркеров и очередей. BullMQ требует эксклюзивных соединений, так как использует блокирующие команды Redis (например, `BRPOP`).
        
    -   **Проблема переиспользования:** Если попытаться использовать один и тот же инстанс `ioredis` для кэширования и для BullMQ, приложение может зависнуть, когда воркер BullMQ переведет соединение в режим блокирующего ожидания, а код кэширования попытается выполнить обычную команду (например, `GET`).
        
    -   **Решение:** BullMQ воркеры должны создавать свои собственные соединения Redis (см. `about/6.md`).
        
4.  **Настройки для BullMQ (только для справки):**
    
    -   **Примечание:** Хотя этот клиент не используется для BullMQ, при создании инстанса `ioredis` для бизнес-кэша также рекомендуется установить опцию `maxRetriesPerRequest: null` для консистентности и избежания потенциальных проблем, если в будущем потребуется переиспользование (хотя это не рекомендуется).
        
5.  **Логирование:** Подписаться на события соединения (`connect`, `ready`, `error`, `close`) и логировать их через `src/utils/logger`.
    
    -   _Пример:_ `logger.info('Redis connected')`.
        
    -   _Пример:_ `logger.error('Redis connection error', { error })`.
        
5.  **Экспорт:** Экспортировать инстанс `Redis`.
    

## 3\. Репозиторий Кэша (`src/infrastructure/redis/cache.js`)

Создать абстракцию для работы с бизнес-данными, чтобы остальной код не знал про ключи и JSON.parse.

**Константы:**

-   `KEY_PREFIX`: `ticket-ai:org:` (все ключи должны начинаться с этого префикса).
    

**Методы для реализации:**

1.  **`getOrgDatasets(orgId)`**
    
    -   _Вход:_ `orgId` (string).
        
    -   _Логика:_ Выполнить `GET ticket-ai:org:{orgId}`.
        
    -   _Обработка:_ Если результат есть -> `JSON.parse` -> вернуть объект `{ adminKbId, historyKbId }`. Если нет -> вернуть `null`.
        
    -   _Ошибки:_ Обернуть в `try/catch`, логировать ошибки парсинга.
        
2.  **`setOrgDatasets(orgId, { adminKbId, historyKbId })`**
    
    -   _Вход:_ `orgId`, объект с ID баз.
        
    -   _Логика:_ Выполнить `SET ticket-ai:org:{orgId}`. Значение: `JSON.stringify(...)`.
        
    -   _TTL:_ Без TTL (храним вечно, пока не будет явной очистки).
        
3.  **`msetOrgDatasets(mappings)`** (Для Cache Warming)
    
    -   _Вход:_ Массив объектов `[{ orgId, adminKbId, historyKbId }, ...]`.
        
    -   _Логика:_ Использовать `pipeline` или `mset` для массовой вставки.
        
    -   _Цель:_ Быстрая инициализация при старте сервиса.
        
4.  **`deleteOrgDatasets(orgId)`**
    
    -   _Логика:_ `DEL ticket-ai:org:{orgId}`.
        
5.  **`flushCache()`** (Для тестов или полного сброса)
    
    -   _Логика:_ Удалить все ключи по паттерну `ticket-ai:org:*` (использовать `SCAN` + `DEL`, чтобы не затронуть ключи очередей BullMQ!).

# Acceptance Criteria (Критерии приемки)

1.  \[ \] Установлен пакет `ioredis`.
    
2.  \[ \] При запуске приложения в логах появляются записи: `Redis connected` -> `Redis ready`.
    
3.  \[ \] Подключение успешно работает с включенной аутентификацией (если задан `REDIS_PASSWORD` в `.env`).
    
4.  \[ \] Инстанс Redis настроен с `maxRetriesPerRequest: null` (для консистентности, хотя этот клиент не используется для BullMQ).
    
5.  \[ \] **Connection Isolation:** Клиент Redis для кэширования изолирован от соединений BullMQ. При одновременной работе воркеров BullMQ и операций кэширования не возникает зависаний или ошибок.
    
6.  \[ \] Реализован модуль `cache.js` с префиксом ключей `ticket-ai:org:`.
    
7.  \[ \] Данные корректно сериализуются/десериализуются (JSON).
    
8.  \[ \] Метод `flushCache` очищает только кэш организаций, не удаляя данные очередей.
