# Техническое задание: Fast Lane Worker - Этап 2: Логика поиска (Retrieval Logic)

**Контекст:** Задача `CMD_GEN_RESPONSE` в `about/8.md` включает в себя поиск, подсчет токенов, обрезку контекста и генерацию. На втором этапе реализуется получение чанков из баз знаний без генерации ответа.

**Цель:** Реализовать базовую структуру Fast Lane Worker и логику поиска чанков из баз знаний (Admin KB и History KB) с использованием OrganizationService.

## 1. Задачи реализации

### 1.1 Реализовать базовую структуру воркера

**Назначение:** Создать файл `src/workers/fastLaneWorker.js` с маршрутизацией задач.

**Задачи:**

1.  Создать файл `src/workers/fastLaneWorker.js`.
    
2.  Реализовать маршрутизацию задач через `switch` по `job.name`:
    
    -   `CMD_GEN_RESPONSE` — обработчик для генерации ответа (реализуется на этом этапе частично).
        
    -   Другие команды (заглушки для будущих этапов).
        
3.  Реализовать обработчик `CMD_GEN_RESPONSE` с шагами:
    
    -   **Шаг 1: Identify Datasets** — получение ID баз знаний через OrganizationService.
        
    -   **Шаг 2: Retrieval** — параллельный поиск чанков из обеих баз.
        
    -   **Шаг 3: Логирование** — логирование найденных чанков и возврат результата в `resultQueue`.
        
4.  Обработка ошибок:
    
    -   Использовать `ErrorHandler` для нормализации ошибок (если доступен).
        
    -   Отправка ошибок в `resultQueue` с корректным форматом.

**Зависимости:**

-   `OrganizationService` (должен быть реализован на этапе `14_5.md` или `14_6.md`).
    
-   `difyApi` (HTTP клиент Dify, должен быть реализован в `about/5.md`).
    
-   `resultQueue` (очередь результатов, должна быть реализована в `about/6.md`).
    
-   Логгер.

### 1.2 Интеграция с OrganizationService

**Назначение:** Получить ID баз знаний для организации.

**Задачи:**

1.  Вызвать `OrganizationService.getKbIdsOrThrow(orgId)` для получения ID баз:
    
    -   `adminKbId` — ID базы знаний для файлов.
        
    -   `historyKbId` — ID базы знаний для истории тикетов.
        
2.  Обработать ошибку `KbNotFoundError`:
    
    -   Если базы не найдены, вернуть ошибку в `resultQueue` с корректным форматом.
        
    -   Логировать ошибку для отладки.

**Зависимости:**

-   `OrganizationService` (метод `getKbIdsOrThrow`).

### 1.3 Параллельный поиск чанков

**Назначение:** Получить релевантные чанки из обеих баз знаний.

**Задачи:**

1.  Реализовать параллельный вызов `difyApi.retrieveChunks` для обеих баз:
    
    -   Для `adminKbId`: запрос Top-3 чанков.
        
    -   Для `historyKbId`: запрос Top-2 чанков.
        
    -   Использовать `Promise.all` для параллельного выполнения запросов.
        
2.  Обработать ошибки поиска:
    
    -   **Graceful degradation:** Если одна база пуста или вернула ошибку, вернуть пустой массив для этой базы.
        
    -   Логировать предупреждения при ошибках поиска (но не прерывать выполнение).
        
    -   Продолжить работу с доступными чанками.
        
3.  Структурировать результаты:
    
    -   `adminChunks` — массив чанков из Admin KB.
        
    -   `historyChunks` — массив чанков из History KB.

**Зависимости:**

-   `difyApi.retrieveChunks` (метод должен быть реализован в `about/5.md`).

### 1.4 Логирование результатов

**Назначение:** Залогировать найденные чанки и вернуть результат для проверки.

**Задачи:**

1.  Залогировать полученные чанки:
    
    -   Количество чанков из каждой базы.
        
    -   Первые несколько чанков для проверки (первые 100 символов каждого).
        
    -   Метаданные (источники, релевантность, если доступны).
        
2.  Вернуть результат в `resultQueue`:
    
    -   Формат результата:
        
        ```javascript
        {
          success: true,
          data: {
            adminChunks: [...],
            historyChunks: [...],
            query: "...",
            orgId: "..."
          }
        }
        ```
        
    -   **Важно:** На этом этапе генерация ответа не выполняется. Результат содержит только найденные чанки.

**Зависимости:**

-   `resultQueue` (очередь результатов).

## 2. Критерий завершения этапа

Воркер получает задачу `CMD_GEN_RESPONSE`, находит чанки из обеих баз знаний, логирует их и возвращает результат в `resultQueue`. Генерация ответа пока не выполняется.

## 3. Тестирование

**Интеграционный тест:**

-   Отправить задачу `CMD_GEN_RESPONSE` в очередь Fast Lane.
    
-   Проверить, что:
    
    -   Воркер получил задачу.
        
    -   ID баз знаний получены через OrganizationService.
        
    -   Чанки найдены из обеих баз (или из доступных баз).
        
    -   Результат отправлен в `resultQueue` с корректным форматом.
        
    -   Чанки залогированы.

## 4. Зависимости от других этапов

-   **Organization Service** (этап 1 или 2) — для получения ID баз знаний.
    
-   **Dify API Client** (`about/5.md`) — для поиска чанков.
    
-   **BullMQ Infrastructure** (`about/6.md`) — для работы с очередями.
    
-   **Error Handler** (`about/10.md`) — для нормализации ошибок (опционально на этом этапе).

6.  \[ \] **Логирование работает:** Найденные чанки залогированы с метаданными.
    
7.  \[ \] **Результат возвращается:** Результат с найденными чанками отправляется в `resultQueue` с корректным форматом.
    
8.  \[ \] **Интеграционный тест проходит:** Тест подтверждает, что весь цикл поиска работает корректно.
