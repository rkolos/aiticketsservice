# Техническое задание: Глобальная обработка ошибок (Error Safety Net)

**Контекст:** У микросервиса нет HTTP-интерфейса. Единственный способ сообщить внешнему миру о проблеме — отправить сообщение в `ai-results-queue`. Если воркер упадет или выбросит исключение без отправки сообщения, внешний сервис зависнет по таймауту.

**Цель:** Гарантировать, что **любое** исключение (валидация, неизвестная команда, ошибка Dify, системный сбой внутри процессора) перехватывается, нормализуется и отправляется в очередь результатов перед тем, как задача будет помечена как `failed` в BullMQ.

## 1\. Концепция Safe Processor Wrapper

Вместо того чтобы дублировать `try/catch` логику с отправкой `sendResult` в каждом процессоре (Router, Fast, Slow), мы создадим функцию высшего порядка (Higher-Order Function), которая обернет любую бизнес-логику.

### 1.1 Файл `src/utils/safeProcessor.js`

Создать утилиту, которая:

1.  Принимает функцию-процессор (`processorFn`).
    
2.  Возвращает новую асинхронную функцию.
    
3.  Внутри:
    
    -   Выполняет `processorFn`.
        
    -   Если успех: возвращает результат.
        
    -   Если ошибка:
        
        -   Логирует ошибку.
            
        -   Нормализует её через `errorHandler`.
            
        -   **Отправляет payload с ошибкой в `resultQueue`.**
            
        -   Пробрасывает ошибку дальше (`throw`), чтобы BullMQ знал о фейле (для метрик и ретраев).
            

**Псевдокод:**

JavaScript

    const { sendResult } = require('../infrastructure/bullmq/resultQueue');
    const ErrorHandler = require('./errorHandler');
    const logger = require('./logger');
    
    const createSafeProcessor = (processorName, processorFn) => async (job) => {
      try {
        return await processorFn(job);
      } catch (error) {
        // 1. Логирование
        logger.error(`Processor ${processorName} failed`, { 
          jobId: job.id, 
          error: error.message,
          stack: error.stack 
        });
    
        // 2. Инвалидация кэша (если применимо, можно вынести внутрь ErrorHandler)
        if (job.data.orgId) {
           await ErrorHandler.handleDifyResourceError(error, job.data.orgId);
        }
    
        // 3. Формирование ответа для внешнего сервиса
        // Важно: берем meta из job.data, чтобы сервис мог сопоставить ответ
        const errorPayload = ErrorHandler.createErrorPayload(error, job.data.meta || {});
    
        // 4. Отправка в очередь результатов (Гарантированная доставка ошибки)
        try {
          await sendResult(job.name + '_ERROR', errorPayload, job.data.meta);
        } catch (sendError) {
          logger.error('CRITICAL: Failed to send error result', { 
            originalError: error.message,
            sendError: sendError.message 
          });
        }
    
        // 5. Пробрасываем ошибку, чтобы BullMQ пометил задачу как Failed
        // Это запустит механизм Retry (если настроен)
        throw error;
      }
    };
    
    module.exports = createSafeProcessor;

## 2\. Обновление Процессоров

Необходимо убрать избыточные `try/catch` блоки верхнего уровня из самих процессоров и переложить ответственность на Wrapper.

### 2.1 Router Processor (`src/workers/routerProcessor.js`)

Роутер должен обрабатывать случаи неизвестных команд.

**Логика:**

1.  Обернуть экспорт в `createSafeProcessor('Router', ...)`.
    
2.  Внутри: если команда не найдена в списках `FAST` или `SLOW`, выбрасывать ошибку: `throw new Error(\`Unknown command: ${job.name}\`)\`.
    
    -   _Результат:_ Wrapper перехватит это, сформирует JSON с `errorCode: INTERNAL_ERROR` и отправит в очередь ответов. Внешний сервис сразу узнает, что он послал ерунду.
        

### 2.2 Fast & Slow Processors

1.  Обернуть экспорт в `createSafeProcessor`.
    
2.  Убрать дублирование вызова `sendResult` в блоках `catch`. Оставить только специфичную логику (например, специфичные логи).
    

## 3\. Обработка фатальных ошибок (System Level)

Если Redis упал, мы не сможем отправить результат в `ai-results-queue`. Но мы можем хотя бы залогировать это корректно.

### 3.1 Обновление `src/infrastructure/bullmq/factory.js`

Убедиться, что на событиях `error` и `failed` воркера есть детальное логирование.

JavaScript

    worker.on('failed', (job, err) => {
      // Тут можно добавить алерт в Sentry/Telegram в будущем
      logger.error(`Job ${job.id} permanently failed`, { reason: err.message });
    });

## 4\. Расширение ErrorHandler

Добавить новые коды ошибок в `src/utils/errorHandler.js` для прозрачности:

1.  **`UNKNOWN_COMMAND`**: Если Роутер не знает такой задачи.
    
2.  **`ROUTING_ERROR`**: Если не удалось добавить задачу в целевую очередь.
    
3.  **`VALIDATION_ERROR`**: Если отсутствуют обязательные поля (например, `orgId`).

## 6\. Acceptance Criteria (Критерии приемки)

1.  \[ \] **Wrapper реализован:** Создан `createSafeProcessor`.
    
2.  \[ \] **Роутер защищен:** Если отправить неизвестную команду в `ai-entry-queue`, в `ai-results-queue` приходит ответ с ошибкой.
    
3.  \[ \] **Воркеры защищены:** Если внутри обработки `CMD_GEN_RESPONSE` происходит `JSON.parse` ошибка или Dify 500, в `ai-results-queue` приходит ответ с ошибкой.
    
4.  \[ \] **Meta сохраняется:** В сообщении об ошибке поле `meta` соответствует исходному запросу (чтобы внешний сервис мог понять, какая именно задача упала).
    
5.  \[ \] **Код чище:** Из процессоров убрана дублирующая логика отправки ошибок.
