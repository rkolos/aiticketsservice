# Техническое задание: Organization Service - Этап 3: Lazy Loading (Write Operations)

**Контекст:** Модуль `OrganizationService` в `about/7.md` отвечает за синхронизацию, ленивую загрузку и инвалидацию кэша. На третьем этапе реализуется создание баз знаний "на лету" при первом обращении (Lazy Loading), что сложнее предыдущих этапов, так как требует проверки кэша -> запроса к Dify -> создания датасета -> обновления кэша.

**Цель:** Реализовать методы `ensureAdminKb` и `ensureHistoryKb`, которые гарантируют существование баз знаний для организации, создавая их при необходимости. Эти методы используются перед операциями записи (загрузка файлов, архивация тикетов).

## 1. Задачи реализации

### 1.1 Реализовать `ensureAdminKb(orgId)` (Lazy Loading для записи)

**Назначение:** Гарантировать, что база файлов существует. Используется перед загрузкой файлов.

**Метод:**

```javascript
async ensureAdminKb(orgId) {
  // Реализация
}
```

**Алгоритм:**

1.  **Check Cache (Cache First):**
    
    -   Проверить Redis через `redisCache.getOrgDatasets(orgId)`.
        
    -   Если есть `adminKbId` и он не пустой -> вернуть его (быстрый путь).
        
2.  **Check Dify (Failover):**
    
    -   Если в кэше нет `adminKbId`, запросить список датасетов у Dify.
        
    -   Использовать ключ `config.dify.keys.admin` для авторизации.
        
    -   Вызвать `difyApi.listDatasets(adminKey, page, limit)` с пагинацией (или перебором первой страницы, если ожидается небольшое количество датасетов).
        
    -   Фильтровать результаты по имени, соответствующему паттерну `KB_ADMIN_{orgId}`.
        
    -   Если датасет найден -> сохранить `adminKbId` в Redis (используя `redisCache.setOrgDatasets`, не затирая существующий `historyKbId`) и вернуть ID.
        
3.  **Create (Lazy Create):**
    
    -   Если датасет не найден ни в кэше, ни в Dify -> создать новую базу.
        
    -   Вызвать `difyApi.createDataset(adminKey, name, description)` с параметрами:
        
        -   `name`: `KB_ADMIN_{orgId}` (строго по конвенции именования).
            
        -   `description`: `Admin Knowledge Base for organization ${orgId}` (или другое, в зависимости от требований).
            
    -   Использовать Admin Key: `config.dify.keys.admin`.
        
4.  **Update Cache:**
    
    -   Сохранить новый `adminKbId` в Redis через `redisCache.setOrgDatasets(orgId, { adminKbId, historyKbId })`.
        
    -   **Важно:** Не затирать существующий `historyKbId`, если он есть. Если `historyKbId` уже есть в кэше, сохранить оба значения. Если нет, сохранить только `adminKbId` (или `null` для `historyKbId`).
        
5.  **Возврат результата:**
    
    -   Вернуть `adminKbId` (найденный или созданный).

**Зависимости:**

-   `redisCache` (репозиторий кэша, этап `7_1.md`).
    
-   `difyApi` (HTTP клиент Dify, `about/5.md`).
    
-   Конфигурация (`config.dify.keys.admin`).
    
-   Логгер.

**Тестирование:**

-   **Интеграционный тест с реальным Dify (или моком):**
    
    -   **Случай 1: База уже есть в Redis.**
        
        -   Настроить мок Redis, чтобы вернуть `adminKbId`.
            
        -   Вызвать `ensureAdminKb(orgId)`.
            
        -   Проверить, что метод вернул `adminKbId` из кэша без обращения к Dify.
            
    -   **Случай 2: База есть в Dify, но нет в Redis.**
        
        -   Настроить мок Redis, чтобы вернуть `null` или объект без `adminKbId`.
            
        -   Настроить мок Dify API, чтобы вернуть датасет с именем `KB_ADMIN_{orgId}`.
            
        -   Вызвать `ensureAdminKb(orgId)`.
            
        -   Проверить, что метод нашел базу в Dify, сохранил в Redis и вернул `adminKbId`.
            
    -   **Случай 3: Базы нет нигде (создание новой).**
        
        -   Настроить мок Redis, чтобы вернуть `null`.
            
        -   Настроить мок Dify API, чтобы вернуть пустой список датасетов.
            
        -   Настроить мок Dify API для создания датасета, чтобы вернуть новый `adminKbId`.
            
        -   Вызвать `ensureAdminKb(orgId)`.
            
        -   Проверить, что метод создал новую базу, сохранил в Redis и вернул `adminKbId`.
            
    -   **Случай 4: Сохранение historyKbId при обновлении adminKbId.**
        
        -   Настроить мок Redis, чтобы вернуть объект с `historyKbId`, но без `adminKbId`.
            
        -   Настроить мок Dify API для создания датасета.
            
        -   Вызвать `ensureAdminKb(orgId)`.
            
        -   Проверить, что при сохранении в Redis оба значения (`adminKbId` и `historyKbId`) сохранены.

### 1.2 Реализовать `ensureHistoryKb(orgId)` (Lazy Loading для записи)

**Назначение:** Гарантировать, что база истории существует. Используется перед архивацией тикетов.

**Метод:**

```javascript
async ensureHistoryKb(orgId) {
  // Реализация
}
```

**Алгоритм:**

-   Аналогичен `ensureAdminKb`, но с префиксом имени `KB_HISTORY_{orgId}` вместо `KB_ADMIN_{orgId}`.
    
-   Имя датасета: `KB_HISTORY_{orgId}` (строго по конвенции именования).
    
-   Описание: `History Knowledge Base for organization ${orgId}` (или другое, в зависимости от требований).
    
-   Использовать тот же `config.dify.keys.admin`.
    
-   Сохранение в Redis: обновить `historyKbId` в существующей записи организации, не затирая `adminKbId`.

**Зависимости:**

-   Те же, что и для `ensureAdminKb`.

**Тестирование:**

-   Аналогичные интеграционные тесты, как для `ensureAdminKb`, но с префиксом `KB_HISTORY_`.

## 3. Критерий завершения этапа

Lazy Loading работает для обеих баз. Можно использовать в воркерах (например, в Slow Lane Worker) для гарантии существования баз перед операциями (загрузка файлов, архивация тикетов). Методы корректно обрабатывают все три сценария: база в кэше, база в Dify, создание новой.

-   **Этап 2 (`7_2.md`):** Используется `difyApi` для поиска и создания датасетов.

-   **Конфигурация (`about/3.md`):** Для получения Admin Key.

-   **Fast Lane Worker (`about/8.md`):** Метод `ensureHistoryKb` может использоваться перед архивацией тикетов (опционально).

## 7. Особенности реализации

**Важные моменты:**

1.  **Конвенция именования:** Строго следовать паттернам `KB_ADMIN_{orgId}` и `KB_HISTORY_{orgId}`.
    
2.  **Сохранение существующих данных:** При обновлении кэша не затирать существующие значения (`adminKbId` или `historyKbId`).
    
3.  **Обработка ошибок:** При ошибках создания датасета логировать ошибку и выбрасывать исключение для обработки в вызывающем коде.
    
4.  **Логирование:** Логировать все этапы (проверка кэша, поиск в Dify, создание датасета) для отладки.
