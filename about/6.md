

# Техническое задание: Инфраструктура BullMQ (Queues & Workers)

**Контекст:** Микросервис работает асинхронно, получая задачи из Redis и отправляя результаты обратно. Нам необходимо настроить библиотеку `bullmq` для работы с тремя очередями, реализовать паттерн "Fast/Slow Lane" через настройки конкурентности (concurrency) и лимитов (rate limiting), а также подготовить структуру для процессоров.

**Цель:** Реализовать модуль `src/infrastructure/bullmq`, инициализировать очереди и воркеры, подключить их к Redis (с учетом аутентификации) и настроить логирование событий.

## 3\. Фабрика Воркеров (`src/infrastructure/bullmq/factory.js`)

Создать утилиту для стандартизированного создания воркеров. Это нужно, чтобы не дублировать код подключения к Redis и логирования ошибок.

**Функция `createWorker(queueName, processor, options)`**:

1.  **Connection:** Настроить подключение к Redis.
    
    -   **Критически важно:** BullMQ требует **эксклюзивных соединений** для своих воркеров. Нельзя использовать один и тот же инстанс `ioredis` для обычного кэширования (`src/infrastructure/redis/client.js`) и для воркеров BullMQ.
        
    -   **Проблема:** BullMQ использует блокирующие команды Redis (например, `BRPOP`, `BLPOP`), которые переключают соединение в режим блокирующего ожидания. Если попытаться выполнить обычную команду (например, `GET`) на клиенте, который находится в режиме блокирующего ожидания очереди, приложение зависнет или выбросит ошибку.
        
    -   **Решение:** Фабрика воркеров должна создавать **новые инстансы `ioredis`**, а не импортировать синглтон, используемый для бизнес-кэша.
        
    -   **Настройки подключения:**
        
        -   Использовать настройки из `src/config`: `host`, `port`, **`password`**.
            
        -   Создать новый инстанс `ioredis` с опцией `maxRetriesPerRequest: null` (обязательное требование BullMQ).
            
        -   BullMQ требует минимум **два соединения** для каждого воркера:
            
            1.  **Соединение для подписки/блокировки:** Используется для блокирующих команд (`BRPOP`, `BLPOP`).
                
            2.  **Соединение для команд:** Используется для обычных команд (например, `SET`, `GET`, `DEL`).
                
        -   BullMQ автоматически создает эти соединения при передаче объекта `connection` в конструктор `Worker`.
            
    -   **Пример создания соединения:**
        
        JavaScript
        
            const Redis = require('ioredis');
            
            const connection = new Redis({
              host: config.redis.host,
              port: config.redis.port,
              password: config.redis.password,
              maxRetriesPerRequest: null  // Обязательно для BullMQ
            });
            
            const worker = new Worker(queueName, processor, {
              connection,
              defaultJobOptions: {
                attempts: 3,
                backoff: {
                  type: 'exponential',
                  delay: 1000  // 1s, 2s, 4s
                }
              },
              // ... другие опции (concurrency, limiter и т.д.)
            });
        
    -   **Важно:** Не импортировать и не использовать синглтон из `src/infrastructure/redis/client.js` для BullMQ воркеров. Каждый воркер должен иметь свои собственные соединения.
        
2.  **Options:** Мержить дефолтные настройки с переданными `options`.
    
    -   **Дефолтные настройки:**
        
        -   `removeOnComplete: { count: 1000 }` — хранить последние 1000 успешно выполненных задач.
            
        -   `removeOnFail: { count: 5000 }` — хранить последние 5000 неудачных задач для анализа.
            
    -   **Стратегия Retry (Backoff):**
        
        -   **Проблема:** Если Dify упал (502 Bad Gateway) или временно недоступен, воркер может попытаться перезапустить задачу мгновенно, создавая дополнительную нагрузку на лежащий сервис и усугубляя проблему.
            
        -   **Решение:** Настроить стратегию повторных попыток с экспоненциальной задержкой (exponential backoff), чтобы дать сервису время на восстановление.
            
        -   **Настройки:**
            
            JavaScript
            
                defaultJobOptions: {
                  attempts: 3,
                  backoff: {
                    type: 'exponential',
                    delay: 1000  // 1s, 2s, 4s
                  }
                }
            
        -   **Объяснение:**
            
            -   `attempts: 3` — максимум 3 попытки выполнения задачи (1 основная + 2 повторные).
                
            -   `type: 'exponential'` — экспоненциальная задержка между попытками.
                
            -   `delay: 1000` — начальная задержка 1 секунда. При каждой следующей попытке задержка удваивается:
                
                -   1-я попытка: выполняется сразу.
                    
                -   2-я попытка: через 1 секунду после первой неудачи.
                    
                -   3-я попытка: через 2 секунды после второй неудачи.
                    
                -   4-я попытка: через 4 секунды после третьей неудачи (но не выполнится, так как attempts: 3).
                    
        -   **Применение:** Эти настройки должны применяться на уровне воркера через `defaultJobOptions`, чтобы все задачи в очереди использовали эту стратегию по умолчанию.
            
        -   **Конфигурация:** Значения `attempts` и `backoff.delay` должны быть настраиваемыми через конфиг (например, `config.workers.retry.attempts` и `config.workers.retry.backoffDelay`), чтобы можно было изменять их без пересборки кода.
            
        -   **Важно:** Стратегия retry применяется только для временных ошибок (сетевые ошибки, 502, 503, таймауты). Для постоянных ошибок (например, 404 Not Found, 401 Unauthorized) повторные попытки не имеют смысла и задача должна быть помечена как Failed сразу.
            
3.  **Events:**
    
    -   `completed`: Логировать `Job {id} completed`.
        
    -   `failed`: Логировать `Job {id} failed: {reason}` через `logger.error`.
        
    -   `error`: Логировать критические ошибки самого воркера (потеря соединения и т.д.).
        
4.  **Return:** Инстанс `Worker`.

## 6\. Инициализация Воркеров (`src/infrastructure/bullmq/index.js`)

Этот файл собирает всё вместе и запускает слушателей.

**Важно:** Все настройки воркеров (включая `concurrency`) должны браться из конфига (`config.workers.*`), который читает значения из `.env` файла. Это позволяет тюнить производительность без пересборки контейнера.

**Воркер 1: Fast Lane (Интерактивная)**

-   **Очередь:** `ai-interactive-queue`.
    
-   **Processor:** Импорт из `src/workers/fastLaneProcessor.js`.
    
-   **Настройки:**
    
    -   `concurrency`: Использовать значение из конфига `config.workers.fastLane.concurrency` (по умолчанию `15`, настраивается через `WORKER_FAST_LANE_CONCURRENCY` в `.env`).
        
        -   **Рекомендуется начать с консервативного значения** (10-20), которое можно установить в `.env` файле.
        
        -   **Важно:** Значение `concurrency` определяет количество одновременных соединений к Dify API, которые может открыть один инстанс воркера. При использовании self-hosted Dify (Docker Compose) его база данных (Postgres) и векторная база (Weaviate/Qdrant) могут не выдержать высокий параллелизм, особенно при тяжелых операциях генерации.
            
        -   **Риск перегрузки:** Если установить `concurrency: 50`, один инстанс воркера может одновременно открыть 50 соединений к Dify. Стандартная конфигурация Dify (Docker Compose) часто не рассчитана на такой параллелизм и может привести к:
            
            -   Перегрузке базы данных Postgres (блокировки, таймауты).
                
            -   Перегрузке векторной базы (Weaviate/Qdrant) при параллельных запросах поиска.
                
            -   Исчерпанию ресурсов (CPU, память) на сервере Dify.
                
            -   Ошибкам таймаута и деградации производительности.
                
        -   **Рекомендация:** 
            
            1.  Начать с консервативного значения `concurrency: 10-20`.
                
            2.  Провести нагрузочное тестирование самого Dify (не только микросервиса) с постепенным увеличением нагрузки.
                
            3.  Мониторить метрики Dify (использование CPU, памяти, время ответа API, ошибки базы данных).
                
            4.  Повышать `concurrency` только после подтверждения, что Dify стабильно справляется с текущей нагрузкой.
                
            5.  Учитывать, что при масштабировании (запуске нескольких инстансов воркеров) общая нагрузка на Dify будет умножена на количество инстансов.
                
        -   **Конфигурация:** Значение `concurrency` должно быть настраиваемым через переменную окружения `WORKER_FAST_LANE_CONCURRENCY` в `.env` файле (см. `about/3.md`). Это позволяет тюнить производительность без пересборки контейнера.
            
            -   В коде использовать значение из конфига: `config.workers.fastLane.concurrency`.
                
            -   Значение по умолчанию: `15` (консервативное значение между 10-20).
                
            -   **Важно:** Не хардкодить значение `concurrency` в `index.js` или других файлах — оно должно браться из конфига, который читает из `.env`.
            

**Воркер 2: Slow Lane (Фоновая)**

-   **Очередь:** `ai-background-queue`.
    
-   **Processor:** Импорт из `src/workers/slowLaneProcessor.js`.
    
-   **Настройки:**
    
    -   `concurrency`: Использовать значение из конфига `config.workers.slowLane.concurrency` (по умолчанию `2`, настраивается через `WORKER_SLOW_LANE_CONCURRENCY` в `.env`).
        
        -   **Жесткое ограничение для предотвращения перегрузки Dify.**
        
        -   **Важно:** Для задач загрузки файлов процесс индексации документов (Embedding Generation) очень ресурсоемкий. Даже при `concurrency: 5` одновременная обработка нескольких больших файлов может привести к перегрузке Dify и падению по OOM или таймауту. Подробнее см. `about/9.md`.
            
    -   `limiter`:
        
        -   **Для задач загрузки файлов (`CMD_KB_ADD_FILE`):**
            
            -   `max`: **1** (максимум 1 задача).
                
            -   `duration`: **1000-2000** (в 1-2 секунды).
                
            -   **Критично:** 10 файлов в секунду — это эквивалентно DDoS-атаке на Dify. Процесс индексации требует загрузки файла, парсинга, генерации эмбеддингов и сохранения в векторную базу. Подробнее см. `about/9.md`.
                
        -   **Для других задач:** Можно использовать более мягкие ограничения, но общее ограничение `concurrency: 2` все равно ограничит частоту обработки.
            
        -   **Конфигурация:** 
            
            -   Значение `concurrency` должно быть настраиваемым через переменную окружения `WORKER_SLOW_LANE_CONCURRENCY` в `.env` файле (см. `about/3.md`). Это позволяет тюнить производительность без пересборки контейнера.
                
            -   В коде использовать значение из конфига: `config.workers.slowLane.concurrency`.
                
            -   Значение по умолчанию: `2`.
                
            -   **Важно:** Не хардкодить значение `concurrency` в `index.js` или других файлах — оно должно браться из конфига, который читает из `.env`.
                
            -   Настройки Rate Limiter также должны быть настраиваемыми через конфиг (например, `config.workers.slowLane.rateLimiter.fileUpload`).
            
        -   _Обоснование:_ Защита Dify API от перегрузки при массовой загрузке файлов. Жесткие ограничения предотвращают падение Dify по OOM или таймауту при одновременной загрузке нескольких больших файлов.
            

**Экспорт:** Функция `initWorkers()`, которая создает и возвращает массив или объект с воркерами.

**Пример использования конфига:**

JavaScript

    const config = require('../config');
    
    const fastLaneWorker = createWorker(
      QUEUES.INTERACTIVE,

    const slowLaneWorker = createWorker(

      {
        concurrency: config.workers.slowLane.concurrency, // Из .env: WORKER_SLOW_LANE_CONCURRENCY
        // ... другие опции
      }
    );

## 7\. Обновление точки входа (`src/index.js`)

2.  Вызвать `initWorkers()` **после** успешной проверки подключения к Redis (см. `about/4.md`).
    
3.  Добавить **Graceful Shutdown**:
    
    -   При получении сигнала `SIGTERM` / `SIGINT`:
        
        1.  `logger.info('Shutting down...')`
            
        2.  Вызвать `worker.close()` для обоих воркеров (ждет завершения текущих задач).
            
            -   **Важно:** Метод `worker.close()` автоматически закроет соединения Redis, созданные для этого воркера.
                
        3.  Вызвать `resultQueue.close()`.
            
            -   **Важно:** Метод `resultQueue.close()` автоматически закроет соединение Redis, созданное для этой очереди.
                
        4.  Закрыть соединение Redis клиента кэша (`src/infrastructure/redis/client.js`).
            
            -   **Важно:** Это отдельное соединение, не связанное с BullMQ, поэтому его нужно закрывать отдельно.
                
        5.  `process.exit(0)`.
            

# Acceptance Criteria (Критерии приемки)

1.  \[ \] Установлен `bullmq`.
    
2.  \[ \] Созданы константы имен очередей.
    
3.  \[ \] **Exclusive Connections:** Фабрика воркеров создает новые инстансы `ioredis` для каждого воркера, а не использует синглтон из `src/infrastructure/redis/client.js`. Каждый воркер имеет свои собственные соединения, изолированные от клиента кэширования.
    
4.  \[ \] Файл `factory.js` корректно передает `REDIS_PASSWORD` и опцию `maxRetriesPerRequest: null`.
    
5.  \[ \] При запуске приложения в логах нет ошибок подключения BullMQ.
    
6.  \[ \] Интеграционный тест (ручной):
    
    -   При добавлении задачи в `ai-interactive-queue` через внешний инструмент, микросервис подхватывает её, логирует и помечает как `completed`.
        
7.  \[ \] Rate Limiter настроен для `ai-background-queue`.
    
8.  \[ \] При нажатии Ctrl+C приложение корректно завершает работу, дожидаясь (или пытаясь дождаться) окончания активных джобов.
    
9.  \[ \] **Concurrency Configuration:** Значение `concurrency` для Fast Lane воркера настраивается через переменную окружения `WORKER_FAST_LANE_CONCURRENCY` в `.env` файле, читается через конфиг (`config.workers.fastLane.concurrency`) и по умолчанию установлено в консервативное значение (15). Значение не хардкодится в коде, что позволяет тюнить производительность без пересборки контейнера.
    
10. \[ \] **Load Testing Readiness:** Документация или комментарии в коде указывают на необходимость нагрузочного тестирования Dify перед увеличением `concurrency` выше рекомендуемых значений.
    
11. \[ \] **Connection Isolation:** При одновременной работе воркеров BullMQ и операций кэширования (например, `redisCache.getOrgDatasets`) не возникает зависаний или ошибок, что подтверждает корректную изоляцию соединений.
    
12. \[ \] **Retry Strategy:** В настройках воркеров (через `defaultJobOptions`) настроена стратегия Retry с экспоненциальной задержкой: `attempts: 3`, `backoff: { type: 'exponential', delay: 1000 }`.
    
13. \[ \] **Exponential Backoff:** При временных ошибках (502, 503, таймауты, сетевые ошибки) задачи автоматически повторяются с экспоненциальной задержкой (1s, 2s, 4s), предотвращая дополнительную нагрузку на лежащий сервис.
    
14. \[ \] **Retry Configuration:** Настройки retry (`attempts` и `backoff.delay`) настраиваются через конфиг (например, `config.workers.retry.attempts` и `config.workers.retry.backoffDelay`), что позволяет изменять их без пересборки кода.
    
15. \[ \] **Permanent Errors Handling:** Постоянные ошибки (404, 401) не вызывают повторных попыток — задача сразу помечается как Failed, что предотвращает бессмысленные retry для некорректных запросов.
