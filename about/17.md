# Техническое задание: Fast Lane Worker - Этап 3: Логика сборки контекста (Context Assembly & Pruning)

**Контекст:** Задача `CMD_GEN_RESPONSE` в `about/8.md` включает в себя поиск, подсчет токенов, обрезку контекста и генерацию. На третьем этапе реализуется сборка и обрезка контекста с учетом всех лимитов (Dify Input Variable, Dify POST Request, Model Context Window).

**Цель:** Реализовать сборку контекста из чанков и истории, а также обрезку контекста при превышении лимитов с учетом приоритетов (adminChunks важнее historyChunks).

## 1. Задачи реализации

### 1.1 Реализовать Context Assembly

**Назначение:** Склеить чанки из обеих баз знаний и отформатировать историю в единый контекст.

**Задачи:**

1.  **Склеить чанки в структурированную строку Markdown:**
    
    -   Объединить `adminChunks` и `historyChunks` в единую строку.
        
    -   Формат склейки:
        
        ```markdown
        ## Контекст из базы знаний
        
        ### Административная база
        
        [Содержимое чанка 1]
        
        [Содержимое чанка 2]
        
        ...
        
        ### История тикетов
        
        [Содержимое чанка 1]
        
        [Содержимое чанка 2]
        
        ...
        ```
        
    -   Если чанков нет, вернуть пустую строку или сообщение "Контекст не найден".
        
2.  **Использовать утилиту `formatTicketHistory` для форматирования истории:**
    
    -   Вызвать `historyFormatter.formatTicketHistory(history)` для преобразования истории в структурированный Markdown.
        
    -   Если история уже в формате Markdown, утилита должна валидировать и нормализовать формат.
        
3.  **Структурировать переменные для Dify Workflow:**
    
    -   `context` — склеенные чанки (строка Markdown).
        
    -   `history` — отформатированная история (строка Markdown).
        
    -   `query` — исходный запрос пользователя (строка).

**Зависимости:**

-   `historyFormatter` (утилита из этапа `14_1.md`).
    
-   Чанки из этапа `14_2.md`.

### 1.2 Реализовать Context Pruning

**Назначение:** Обрезать контекст и историю при превышении лимитов с учетом приоритетов.

**Задачи:**

1.  **Интегрировать `tokenCounter` для подсчета токенов:**
    
    -   Использовать `tokenCounter.estimateTotalTokens(context, history, query, modelName)` для подсчета токенов всех компонентов.
        
    -   Получить модель из конфигурации: `config.model.name`.
        
2.  **Реализовать многоуровневую проверку лимитов:**
    
    Проверить лимиты в следующем порядке и выбрать минимальный:
    
    1.  **Лимит Dify на размер входной переменной:**
        
        -   `config.dify.workflow.maxInputVariableSize` (например, 48KB в символах или токенах).
        
    2.  **Лимит Dify на размер POST-запроса:**
        
        -   `config.dify.workflow.maxRequestBodySize` (например, 10MB).
        
    3.  **Лимит контекстного окна модели:**
        
        -   `config.model.contextWindow` (например, 8192 токенов для gpt-3.5-turbo).
        
    -   Выбрать минимальный лимит из трех для каждой переменной отдельно (`context` и `history`).
        
3.  **Реализовать стратегию обрезки:**
    
    -   **Проверка лимитов для каждой переменной отдельно:**
        
        -   Проверить размер `context` (чанки) относительно лимита.
            
        -   Проверить размер `history` относительно лимита.
            
        -   Если обе переменные превышают лимиты, обрезать обе.
            
    -   **Приоритет при обрезке:**
        
        -   Сохранить все чанки из `adminChunks` (они важнее для ответа).
            
        -   Обрезать чанки из `historyChunks` при необходимости.
            
        -   Обрезать `history` (история диалога) при необходимости.
            
    -   **Алгоритм обрезки:**
        
        1.  Если `context` превышает лимит:
            
            -   Сохранить все `adminChunks`.
                
            -   Обрезать `historyChunks` с конца массива до тех пор, пока `context` не уложится в лимит.
                
            -   Если после удаления всех `historyChunks` лимит все еще превышен, обрезать содержимое отдельных чанков из `adminChunks` (с конца текста).
                
        2.  Если `history` превышает лимит:
            
            -   Обрезать историю с конца (удалить старые сообщения).
                
            -   Если история в формате массива, удалить последние элементы.
                
            -   Если история в формате Markdown, обрезать строку с конца.
                
    -   **Логирование обрезки:**
        
        -   Залогировать предупреждение при обрезке с указанием:
            
            -   Причины обрезки (какой лимит превышен).
                
            -   Количества отброшенных чанков.
                
            -   Количества отброшенных токенов/символов.
                
            -   Размера контекста до и после обрезки.

**Зависимости:**

-   `tokenCounter` (утилита из этапа `14_1.md`).
    
-   Конфигурация (`config.dify.workflow.maxInputVariableSize`, `config.dify.workflow.maxRequestBodySize`, `config.model.contextWindow`).

### 1.3 Тестирование обрезки

**Назначение:** Убедиться, что обрезка работает корректно во всех сценариях.

**Задачи:**

1.  **Unit-тест с "длинными" входными данными:**
    
    -   Создать тест с большими чанками (например, по 2000 токенов каждый).
        
    -   Создать тест с длинной историей (например, 10000 токенов).
        
    -   Проверить корректность обрезки при превышении каждого типа лимита:
        
        -   Превышение лимита Dify Input Variable.
            
        -   Превышение лимита Dify POST Request.
            
        -   Превышение лимита Model Context Window.
            
2.  **Проверить приоритеты:**
    
    -   Проверить, что `adminChunks` сохраняются перед `historyChunks`.
        
    -   Проверить, что при обрезке `historyChunks` все `adminChunks` остаются нетронутыми.
        
3.  **Проверить логирование:**
    
    -   Проверить, что предупреждения логируются при обрезке.
        
    -   Проверить, что в логах указаны корректные метрики (количество отброшенных чанков, размер до/после).

**Зависимости:**

-   Unit-тесты с моками `tokenCounter` и конфигурации.
