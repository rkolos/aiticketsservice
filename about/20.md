# Техническое задание: Organization Service - Этап 4: Интеграция инвалидации кэша при ошибках

**Контекст:** Сервис `OrganizationService` в `about/7.md` включает Cache Warming, Lazy Loading, Strict Read и инвалидацию кэша. На четвертом этапе интегрируется автоматическая инвалидация кэша при ошибках Dify (например, `dataset_not_found`, 404 статус).

**Цель:** Интегрировать автоматическую инвалидацию кэша при обнаружении ошибок отсутствия ресурсов в Dify, чтобы решить проблему Stale Cache.

## 1. Задачи реализации

### 1.1 Интеграция с ErrorHandler

**Назначение:** Использовать `ErrorHandler.handleDifyResourceError` для автоматической инвалидации кэша при ошибках Dify.

**Места интеграции:**

1.  **В слое `infrastructure/dify` (рекомендуется):**
    
    -   В интерцепторе ответов Axios или в методах `difyApi` добавить проверку ошибок.
        
    -   При обнаружении ошибки 404 или специфических кодов ошибок Dify (например, `dataset_not_found`, `knowledge_base_not_found`) вызвать `ErrorHandler.handleDifyResourceError(error, orgId)`.
        
2.  **В воркерах (альтернативный вариант):**
    
    -   В обработчиках ошибок воркеров (Fast Lane, Slow Lane) вызывать `ErrorHandler.handleDifyResourceError` перед созданием error payload.
        
    -   Это менее предпочтительно, так как требует дублирования логики в каждом воркере.

**Алгоритм интеграции:**

1.  **В интерцепторе Axios (рекомендуемый подход):**
    
    ```javascript
    // В src/infrastructure/dify/client.js
    axiosInstance.interceptors.response.use(
      (response) => response,
      async (error) => {
        // Проверить, является ли ошибка ошибкой отсутствия ресурса
        if (error.response?.status === 404 || 
            error.response?.data?.code === 'dataset_not_found' ||
            error.response?.data?.code === 'knowledge_base_not_found') {
          
          // Извлечь orgId из контекста запроса (если доступен)
          const orgId = error.config?.metadata?.orgId;
          
          if (orgId) {
            await ErrorHandler.handleDifyResourceError(error, orgId);
          }
        }
        
        return Promise.reject(error);
      }
    );
    ```
    
2.  **В воркерах (альтернативный подход):**
    
    ```javascript
    // В src/workers/fastLaneWorker.js или slowLaneWorker.js
    try {
      // ... выполнение задачи ...
    } catch (error) {
      // Проверить и инвалидировать кэш при необходимости
      await ErrorHandler.handleDifyResourceError(error, orgId);
      
      // Создать error payload
      const errorPayload = ErrorHandler.createErrorPayload(error, jobId, orgId);
      await resultQueue.add('result', errorPayload);
      
      throw error; // Для BullMQ retry
    }
    ```

**Зависимости:**

-   `ErrorHandler` (должен быть реализован в `about/10.md`).
    
-   `OrganizationService` (для инвалидации кэша, этап `14_5.md`).
    
-   `difyApi` (HTTP клиент Dify, `about/5.md`).

**Тестирование:**

-   **Интеграционный тест:**
    
    -   Симулировать ошибку 404 от Dify API (например, при запросе несуществующего датасета).
        
    -   Проверить, что `ErrorHandler.handleDifyResourceError` вызван с корректными параметрами.
        
    -   Проверить, что `OrganizationService.invalidateOrgCache` вызван для соответствующей организации.
        
    -   Проверить, что ключ организации удален из Redis.

### 1.2 Тестирование восстановления

**Назначение:** Убедиться, что после инвалидации кэша следующий запрос создает новую базу или актуализирует данные.

**Сценарий теста:**

1.  **Начальное состояние:**
    
    -   В Redis есть запись: `org:1 -> { adminKbId: 'ds-123' }`.
        
    -   Датасет `ds-123` удален в Dify (вручную или симулировано).
        
2.  **Действие:**
    
    -   Воркер пытается использовать `adminKbId: 'ds-123'` для операции (например, загрузка файла).
        
    -   Dify возвращает ошибку 404 (Dataset Not Found).
        
3.  **Проверка инвалидации:**
    
    -   Проверить, что `ErrorHandler.handleDifyResourceError` вызван.
        
    -   Проверить, что ключ `org:1` удален из Redis.
        
4.  **Проверка восстановления:**
    
    -   Вызвать `OrganizationService.ensureAdminKb(orgId)`.
        
    -   Проверить, что метод создает новую базу в Dify (так как кэш инвалидирован).
        
    -   Проверить, что новый `adminKbId` сохранен в Redis.

**Зависимости:**

-   Интеграционный тест с реальным Dify (или качественным моком) и Redis.

## 2. Критерий завершения этапа

Автоматическая инвалидация кэша работает при ошибках Dify. Stale cache проблема решена. После инвалидации кэша следующий запрос корректно создает новую базу или актуализирует данные.

## 3. Интеграция с предыдущими этапами

-   **Этап 1 (`14_5.md`):** Используется метод `invalidateOrgCache` для удаления ключа из Redis.
    
-   **Этап 2 (`14_6.md`):** Используется метод `ensureAdminKb` для проверки восстановления после инвалидации.

## 4. Зависимости от других этапов

-   **Error Handler (`about/10.md`):** Метод `handleDifyResourceError` должен быть реализован.
    
-   **Organization Service (этапы `14_5.md`, `14_6.md`):** Методы `invalidateOrgCache` и `ensureAdminKb` должны быть реализованы.
    
-   **Dify API Client (`about/5.md`):** Интерцепторы Axios должны быть настроены для передачи метаданных (например, `orgId`) в контексте запроса.

## 5. Интеграция с другими модулями

-   **Fast Lane Worker (`14_4.md`):** Инвалидация кэша будет применяться при ошибках поиска чанков или генерации ответа.
    
-   **Slow Lane Worker (`14_11.md`):** Инвалидация кэша будет применяться при ошибках загрузки файлов или архивации тикетов.
