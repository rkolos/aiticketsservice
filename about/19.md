

# Техническое задание: Воркер Быстрой Очереди (Fast Lane)

**Контекст:** Инфраструктура очередей (BullMQ) настроена, клиент Dify готов (включая метод `retrieveChunks`), сервис управления данными (`OrganizationService`) реализован. Необходимо реализовать логику обработки задач в очереди `ai-interactive-queue`.

**Цель:** Реализовать файл `src/workers/fastLaneWorker.js`, который будет разбирать входящие задачи по их типу, реализовывать паттерн **External RAG** (Поиск -> Сборка контекста -> Генерация) и отправлять результат.

## 1\. Структура Воркера

Воркер должен быть реализован как функция-процессор, передаваемая в BullMQ `Worker`.

### 1.1 Требования к многопоточности и масштабированию (Concurrency Safety)

Для гарантии корректной работы при запуске множества экземпляров воркеров:

1.  **Полная Stateless-архитектура:** Воркер не должен сохранять состояние.
    
2.  **Изоляция соединений Redis:** Каждый экземпляр воркера (процесс) обязан создавать собственные соединения с Redis (для блокировок и очередей).
    
3.  **Lock Duration:** Установить `lockDuration` (например, 60 сек) с запасом, превышающим тайм-аут Dify API.
    
4.  **Idempotency:** Быть готовым к повторной обработке задач.
    

### 1.2 Логика процессора

1.  **Импорт:** `config`, `logger`, `difyApi`, `OrganizationService`, `resultQueue`, утилиты (`llmParser`, `tokenCounter`, `errorHandler`, `billingService`, `historyFormatter`).
    
2.  **Логирование:** `logger.info('Processing fast job', { id: job.id, name: job.name })`.
    
3.  **Маршрутизация (Switch):**
    
    -   `CMD_ANALYZE_NEW_TICKET`
        
    -   `CMD_GEN_RESPONSE`
        
    -   `CMD_TRANSLATE`
        
    -   `CMD_KB_LIST_FILES`
        
    -   `CMD_KB_DELETE_FILE`
        
4.  **Обработка:** Вызов хендлера.
    
5.  **Отправка результата:** `resultQueue.add(...)`.
    
6.  **Обработка ошибок:**
    
    -   `catch (err)`: Логировать.
        
    -   Сформировать пейлоад ошибки (см. п. 3).
        
    -   Отправить в `resultQueue` (чтобы UI получил фидбек).
        
    -   Выбросить ошибку дальше (`throw err`), чтобы BullMQ пометил джоб как Failed и применил стратегию Retry с экспоненциальной задержкой (см. `about/6.md`, раздел "Стратегия Retry (Backoff)").
        
    -   **Важно:** Стратегия retry применяется автоматически для временных ошибок (сетевые ошибки, 502, 503, таймауты). Для постоянных ошибок (404, 401) задача будет помечена как Failed без повторных попыток.
        

## 2\. Реализация Обработчиков (Handlers)

### 2.1 Анализ Тикета (`CMD_ANALYZE_NEW_TICKET`)

-   **Вход:** `text`, `targetLanguage`, `meta`.
    
-   **Ключ:** `config.dify.keys.classifier`.
    
-   **Действия:**
    
    1.  Вызвать `difyApi.runWorkflow(key, inputs)`.
        
        -   `inputs`: `{ message: text, language: targetLanguage }`.
            
    2.  **Парсинг JSON:**
        
        -   Использовать утилиту `parseJsonFromLlm` (очистка от Markdown `json`).
            
    3.  **Валидация:** Проверить поля `title`, `sentiment`.
        
-   **Результат:** `{ title, sentiment }`.
    

### 2.2 Генерация Ответа RAG (`CMD_GEN_RESPONSE`) — **External RAG**

Это самая сложная задача. Мы сами ищем контекст, так как Dify Workflow не умеет динамически переключать базы знаний.

-   **Вход:** `orgId`, `query`, `history` (массив сообщений или Markdown), `meta`.
    
    -   **Формат истории:** Поле `history` должно быть передано в одном из двух форматов:
        
        1.  **Массив сообщений** (предпочтительно, рекомендуется для Main App):
            
            JavaScript
            
                [
                  { role: 'user', content: 'Здравствуйте, у меня проблема...' },
                  { role: 'assistant', content: 'Здравствуйте! Расскажите подробнее...' },
                  { role: 'user', content: 'Не могу войти в систему...' }
                ]
            
            -   **Рекомендация для Main App:** Передавать историю именно в виде массива сообщений, а не в виде отформатированного Markdown. Это обеспечивает гибкость и позволяет воркеру контролировать форматирование.
                
        2.  **Строка Markdown** (альтернативный вариант, если Main App уже выполняет пре-форматирование):
            
            Markdown
            
                User: Здравствуйте, у меня проблема...
                
                Assistant: Здравствуйте! Расскажите подробнее...
                
                User: Не могу войти в систему...
            
            -   **Требования к формату:** Если Main App передает уже отформатированный Markdown, он должен строго следовать структуре с четким разделением реплик через префиксы `User:` и `Assistant:` (или `user:` и `assistant:`, регистр не важен).
                
            -   **Важно:** Если Main App передает "плоский" текст без структурирования, LLM может запутаться и некорректно интерпретировать, где реплика пользователя, а где оператора.
                
    -   **Обработка в воркере:**
        
        -   Если `history` передан как массив, воркер должен отформатировать его в структурированный Markdown перед передачей в Dify Workflow (см. утилиту `formatTicketHistory` в разделе 4.3).
            
        -   Если `history` передан как строка, воркер должен проверить формат и убедиться, что он соответствует структурированному формату с префиксами `User:` / `Assistant:`. Если формат некорректен, залогировать предупреждение.
            
    -   **Важно:** LLM очень чувствительны к формату диалога. Передача истории в структурированном формате с четким разделением реплик критически важна для корректного понимания контекста моделью.
        
    
-   **Действия:**
    
    1.  **Identify Datasets:**
        
        -   Вызвать `OrganizationService.getKbIdsOrThrow(orgId)`.
            
        -   Получить `{ adminKbId, historyKbId }`.
            
    2.  **Retrieval (Parallel):**
        
        -   Использовать ключ **`config.dify.keys.admin`** (так как поиск — это операция с датасетом).
            
        -   Запустить параллельно:
            
            JavaScript
            
                const [adminChunks, historyChunks] = await Promise.all([
                  difyApi.retrieveChunks(adminKey, adminKbId, query, 3), // Top-3 из инструкций
                  difyApi.retrieveChunks(adminKey, historyKbId, query, 2) // Top-2 из истории
                ]);
            -   _Примечание:_ Обработать ошибки. Если одна из баз пуста или удалена, не валить весь запрос, а просто вернуть пустой массив чанков.
                
    3.  **Context Assembly:**
        
        -   Склеить чанки в строку.
            
            Markdown
            
                ### Knowledge Base
                ...content from admin...
                
                ### Ticket History
                ...content from history...
            
        -   Если чанков нет совсем, можно либо прервать, либо отправить пустой контекст (пусть LLM импровизирует).
            
    4.  **Context Pruning (Token Counting & Truncation):**
        
        -   **Назначение:** Предотвратить превышение контекстного окна модели или лимита переменной `input` в Workflow при больших чанках.
            
        -   **Проблема с лимитами Dify:**
            
            -   У Dify (особенно в Workflow) есть жесткие лимиты не только на контекстное окно модели, но и на размер входных переменных (Input Variable Size).
                
            -   Например, переменная `context` или `history`, передаваемая в Workflow, может быть обрезана самим Dify на входе (например, до 48KB или определенного количества токенов), еще до того, как она попадет в LLM.
                
            -   **Риск:** Если не учесть эти лимиты, Dify может обрезать контекст на своей стороне, что приведет к потере важной информации или некорректной работе Workflow.
                
            -   **Решение:** Логика Pruning должна учитывать не только `config.model.contextWindow`, но и лимиты самого Dify на размер POST-запроса и переменных. Необходимо выяснить эти лимиты для используемой версии Dify и добавить их в конфиг обрезки.
                
        -   **Алгоритм:**
            
            1.  **Подсчет токенов:** Использовать утилиту для подсчета токенов (например, `tiktoken` для OpenAI-совместимых моделей или библиотеку, соответствующую используемой модели).
                
                -   Подсчитать токены для:
                    
                    -   Собранного контекста (склеенные чанки)
                        
                    -   Истории тикета (`history`)
                        
                    -   Запроса пользователя (`query`)
                        
                    -   Системного промпта Workflow (если известен)
                        
            2.  **Определение лимита:**
                
                -   **Многоуровневая проверка лимитов:**
                    
                    1.  **Лимит Dify на размер входной переменной** (приоритет 1, самый строгий):
                        
                        -   Получить из конфига: `config.dify.workflow.maxInputVariableSize` (в байтах или токенах).
                            
                        -   Если не задан, использовать значение по умолчанию для вашей версии Dify (например, 48KB или 12000 токенов).
                            
                        -   **Важно:** Этот лимит применяется к каждой переменной отдельно (например, `context` и `history` могут иметь свои лимиты).
                            
                    2.  **Лимит Dify на размер POST-запроса** (приоритет 2):
                        
                        -   Получить из конфига: `config.dify.workflow.maxRequestBodySize` (в байтах).
                            
                        -   Если не задан, использовать значение по умолчанию (например, 1MB или 2MB).
                            
                        -   Учесть общий размер всех переменных (`context`, `history`, `query` и других) в POST-запросе.
                            
                    3.  **Лимит контекстного окна модели** (приоритет 3):
                        
                        -   Получить из конфига: `config.model.contextWindow` (в токенах).
                            
                        -   Если не задан, использовать консервативное значение (например, 80% от контекстного окна модели, чтобы оставить место для ответа).
                            
                        -   Учесть, что это лимит на общий контекст, включая системный промпт, историю, контекст и запрос.
                            
                -   **Выбор минимального лимита:**
                    
                    -   Выбрать минимальный лимит из всех проверенных (Dify Input Variable, Dify POST Request, Model Context Window).
                        
                    -   Это гарантирует, что контекст не будет обрезан ни на одном уровне.
                        
                -   **Конфигурация:**
                    
                    -   Все лимиты должны быть настраиваемыми через конфиг, чтобы можно было адаптировать их под конкретную версию Dify.
                        
                    -   Рекомендуется добавить комментарии в конфиге с указанием версии Dify, для которой установлены лимиты.
                    
            3.  **Обрезка контекста:**
                
                -   **Проверка лимитов для каждой переменной:**
                    
                    -   Проверить размер переменной `context` относительно лимита Dify на входную переменную (`config.dify.workflow.maxInputVariableSize`).
                        
                    -   Проверить размер переменной `history` относительно лимита Dify на входную переменную.
                        
                    -   Проверить общий размер всех переменных относительно лимита Dify на POST-запрос (`config.dify.workflow.maxRequestBodySize`).
                        
                    -   Проверить общий размер (контекст + история + запрос + системный промпт) относительно лимита контекстного окна модели.
                        
                -   **Стратегия обрезки:**
                    
                    -   Если размер переменной `context` превышает лимит Dify на входную переменную:
                        
                        1.  **Приоритет:** Сохранить чанки из `adminChunks` (инструкции) перед `historyChunks` (история тикетов).
                            
                        2.  Сначала удалить последние чанки из `historyChunks` (начиная с конца массива).
                            
                        3.  Если этого недостаточно, удалить последние чанки из `adminChunks`.
                            
                        4.  Если контекст все еще слишком большой, обрезать содержимое отдельных чанков (удалить последние символы/токены из каждого чанка, начиная с последнего).
                            
                    -   Если размер переменной `history` превышает лимит Dify на входную переменную:
                        
                        -   Обрезать историю, сохраняя наиболее свежие реплики (удалять с начала истории).
                            
                    -   Если общий размер POST-запроса превышает лимит Dify:
                        
                        -   Применить обрезку к обеим переменным (`context` и `history`) пропорционально их размеру.
                            
                    -   Если общий размер превышает лимит контекстного окна модели:
                        
                        -   Применить обрезку с учетом приоритетов (инструкции важнее истории).
                            
                    -   После обрезки пересобрать строки контекста и истории.
                        
            4.  **Логирование:**
                
                -   Если была выполнена обрезка, залогировать предупреждение с указанием причины:
                    
                    -   `logger.warn('Context truncated due to Dify input variable limit', { variable: 'context', originalSize, finalSize, limit: config.dify.workflow.maxInputVariableSize })`
                        
                    -   `logger.warn('History truncated due to Dify input variable limit', { variable: 'history', originalSize, finalSize, limit: config.dify.workflow.maxInputVariableSize })`
                        
                    -   `logger.warn('Context truncated due to Dify POST request limit', { originalSize, finalSize, limit: config.dify.workflow.maxRequestBodySize })`
                        
                    -   `logger.warn('Context truncated due to model context window limit', { originalTokens, finalTokens, limit: config.model.contextWindow })`
                        
                -   Указать, сколько чанков было отброшено и какой лимит был превышен.
                    
        -   **Важно:** Обрезка должна происходить **до** формирования финального контекста для отправки в Workflow, чтобы избежать ошибок превышения лимита на стороне Dify.
            
    5.  **Generation:**
        
        -   Использовать ключ **`config.dify.keys.responseWorkflow`** (Support Helper).
            
        -   Вызвать `difyApi.runWorkflow(appKey, inputs)`.
            
        -   `inputs`:
            
            -   `query`: текст вопроса.
                
            -   `history`: история текущего тикета, отформатированная в структурированный Markdown (см. утилиту `formatTicketHistory`).
                
                -   **Формат:** Каждая реплика должна быть четко помечена как `User:` или `Assistant:` для корректного понимания LLM структуры диалога.
                    
            -   **`context`: собранная нами строка.**
                
        -   **Важно — Промпт-инжиниринг:**
            
            -   Workflow в Dify — это "глупая" цепочка узлов. LLM не понимает автоматически, что переменные `history` и `context` представляют собой диалог и контекст для ответа.
                
            -   **Требование:** Системный промпт в узле LLM Workflow "Support Helper" должен явно указывать:
                
                1.  Что `{{history}}` — это история переписки с префиксами `User:` и `Assistant:`.
                    
                2.  Что `{{context}}` — это релевантная информация из базы знаний.
                    
                3.  Как использовать эти данные для ответа на `{{query}}`.
                    
            -   Без правильной связки в промпте передача истории и контекста бесполезна — LLM не сможет корректно их интерпретировать.
                
            -   Подробные требования к системному промпту см. в `about_project.md`, раздел 4, "App 3: Support Helper (Workflow)".
                
    5.  **Result:** Извлечь текст из `outputs.text`.
        
-   **Результат:** `{ text, sources: [...] }` (Источники можно собрать из метаданных чанков с шага 2).
    

### 2.3 Перевод (`CMD_TRANSLATE`)

-   **Вход:** `text`, `targetLang`, `meta`.
    
-   **Ключ:** Можно использовать `classifier` ключ или отдельный, если есть.
    
-   **Действия:**
    
    -   Вызвать `difyApi.runWorkflow` с простым промптом перевода.
        
-   **Результат:** `{ text: translatedText }`.
    

### 2.4 Управление Файлами (`CMD_KB_LIST_FILES` / `DELETE`)

-   **Вход:** `orgId`, `fileId`.
    
-   **Ключ:** **`config.dify.keys.admin`**.
    
-   **Действия:**
    
    1.  Получить `adminKbId` через `OrganizationService.getKbIdsOrThrow(orgId)`.
        
        -   _Важно:_ Если сервис выбросил `KbNotFoundError` для команды `LIST`, перехватить ошибку и вернуть пустой массив `[]` (это нормально, просто база еще не создана).
            
    2.  **List:** `difyApi.listDocuments(adminKey, adminKbId)`.
        
    3.  **Delete:** `difyApi.deleteDocument(adminKey, adminKbId, fileId)`.
        
-   **Результат:** Массив файлов или статус удаления.
    

## 3\. Формат Ответа (Output Payload)

Воркер должен всегда отправлять результат в `ai-results-queue`.

**Успех:**

JavaScript

    {
      status: 'success',
      data: { ... }, // Результат хендлера
      usage: {
        total_tokens: 123, // Из ответа Dify (генерация)
        model: 'gpt-4o'
      },
      meta: job.data.meta // Pass-through context
    }

**Ошибка:**

JavaScript

    {
      status: 'error',
      errorCode: 'KB_NOT_FOUND', // или 'INTERNAL_ERROR', 'JSON_PARSE_ERROR'
      message: 'Human readable message',
      meta: job.data.meta
    }

### 4.1 Парсер LLM (`src/utils/llmParser.js`)

### 4.2 Подсчет токенов (`src/utils/tokenCounter.js`)

Утилита для подсчета токенов в тексте перед отправкой в LLM. Необходима для предотвращения превышения контекстного окна модели.

**Функциональные требования:**

-   **Функция `countTokens(text, modelName)`**
    
    -   **Вход:** Текст для подсчета и (опционально) название модели.
        
    -   **Логика:**
        
        1.  Определить кодировку токенов на основе модели:
            
            -   Для OpenAI-совместимых моделей (gpt-4, gpt-3.5, gpt-4o) использовать библиотеку `tiktoken`.
                
            -   Для других моделей использовать соответствующую библиотеку или приблизительный подсчет (например, 1 токен ≈ 4 символа для английского текста).
                
        2.  Подсчитать количество токенов в тексте.
            
        3.  Вернуть число токенов.
            
    -   **Выход:** `number` (количество токенов).
        
-   **Функция `estimateTotalTokens(context, history, query, modelName)`**
    
    -   **Вход:** Собранный контекст, история тикета, запрос пользователя и название модели.
        
    -   **Логика:** Подсчитать суммарное количество токенов для всех компонентов.
        
    -   **Выход:** `number` (общее количество токенов).
        
-   **Важно:** Утилита должна быть безопасной и не падать при `null`/`undefined` входных данных. В случае ошибки подсчета использовать консервативную оценку (например, 1 токен = 4 символа).

**Зависимости:**

-   Для OpenAI-совместимых моделей: `tiktoken` (npm пакет).
    
-   Для других моделей: соответствующие библиотеки или fallback на приблизительный подсчет.

### 4.3 Форматирование истории тикета (`src/utils/historyFormatter.js`)

Утилита для преобразования истории тикета в структурированный Markdown формат, понятный для LLM.

**Функциональные требования:**

-   **Функция `formatTicketHistory(history)`**
    
    -   **Вход:** История тикета в виде массива сообщений или строки Markdown.
        
        -   Если массив: `[{ role: 'user' | 'assistant', content: string }, ...]`
            
        -   Если строка: уже отформатированный Markdown (вернуть как есть или проверить формат).
            
    -   **Логика:**
        
        1.  Если `history` — массив:
            
            -   Перебрать массив сообщений.
                
            -   Для каждого сообщения сформировать строку в формате:
                
                Markdown
                
                    User: {content}
                    
                    Assistant: {content}
                
            -   Объединить все реплики через двойной перенос строки (`\n\n`).
                
        2.  Если `history` — строка:
            
            -   Проверить, содержит ли строка структурированный формат (наличие `User:` или `Assistant:`).
                
            -   Если формат уже корректен, вернуть строку как есть.
                
            -   Если формат неструктурированный (плоский текст), попытаться распарсить или вернуть с предупреждением в логах.
                
    -   **Выход:** Строка Markdown с четко разделенными репликами пользователя и ассистента.
        
    -   **Пример вывода:**
        
        Markdown
        
            User: Здравствуйте, у меня проблема с доступом к системе.
            
            Assistant: Здравствуйте! Расскажите, пожалуйста, подробнее о проблеме.
            
            User: Не могу войти в личный кабинет, выдает ошибку 404.
            
            Assistant: Понял, проверяю...
        
-   **Важно:** 
    
    -   Утилита должна быть безопасной и не падать при `null`/`undefined` или некорректном формате входных данных.
        
    -   Если входные данные некорректны, вернуть пустую строку или строку с предупреждением и залогировать ошибку.
        
    -   Форматирование должно сохранять исходное содержимое сообщений без изменений (не обрезать, не модифицировать текст).

**Интеграция:**

-   Утилита должна использоваться в обработчике `CMD_GEN_RESPONSE` перед передачей `history` в `difyApi.runWorkflow`.
    
-   Утилита должна использоваться в обработчике `CMD_ARCHIVE_TICKET` перед передачей `fullTicketHistory` в `difyApi.runWorkflow` для суммаризации.

**Требования к Main App:**

-   **Рекомендуется:** Main App должно передавать историю тикета в виде массива сообщений с полями `role` и `content`, а не в виде отформатированного Markdown.
    
-   **Альтернатива:** Если Main App уже выполняет пре-форматирование истории в структурированный Markdown с префиксами `User:` / `Assistant:`, воркер может использовать этот формат напрямую после проверки корректности.
    
-   **Не рекомендуется:** Передача истории в виде "плоского" текста без структурирования, так как это приводит к некорректному пониманию контекста LLM.
        

# Acceptance Criteria (Критерии приемки)

1.  \[ \] **External RAG:** Задача `CMD_GEN_RESPONSE` выполняет сначала поиск (`retrieveChunks` x2), а потом генерацию.
    
2.  \[ \] **Keys:** Поиск и управление файлами используют `admin` ключ, а генерация — ключи приложений.
    
3.  \[ \] **Resilience:** Если поиск в базе истории упал (или вернул пустоту), генерация все равно происходит на основе базы инструкций (graceful degradation).
    
4.  \[ \] **JSON Parser:** Воркер корректно обрабатывает ответы LLM, обернутые в Markdown код-блоки.
    
5.  \[ \] **List Files:** Запрос списка файлов для несуществующей организации возвращает `data: []`, а не ошибку.

6.  \[ \] **Token Counting:** Утилита `tokenCounter` корректно подсчитывает токены для используемых моделей (OpenAI-совместимые через `tiktoken`, другие через fallback).
    
7.  \[ \] **Context Pruning:** При превышении лимита контекста происходит автоматическая обрезка: сначала удаляются чанки из истории, затем из инструкций, с сохранением приоритета инструкций над историей.
    
8.  \[ \] **Limit Configuration:** Лимиты контекста настраиваются через конфиг:
    
    -   `config.model.contextWindow` — лимит контекстного окна модели (в токенах).
        
    -   `config.dify.workflow.maxInputVariableSize` — лимит Dify на размер входной переменной (в байтах или токенах).
        
    -   `config.dify.workflow.maxRequestBodySize` — лимит Dify на размер POST-запроса (в байтах).
        
    -   Используется консервативное значение (80% от окна модели) для резервирования места под ответ, если лимиты не заданы явно.
        
9.  \[ \] **Dify Input Variable Limits:** Логика обрезки учитывает лимиты Dify на размер входных переменных (`context`, `history`) и применяет обрезку до отправки в Workflow, предотвращая обрезку на стороне Dify.
    
10. \[ \] **Multi-Level Limit Checking:** Алгоритм обрезки проверяет лимиты на трех уровнях (Dify Input Variable, Dify POST Request, Model Context Window) и выбирает минимальный лимит для гарантии отсутствия обрезки на любом уровне.
    
11. \[ \] **Pruning Logging:** При выполнении обрезки контекста логируется предупреждение с указанием:
    
    -   Причины обрезки (какой лимит был превышен: Dify Input Variable, Dify POST Request, Model Context Window).
        
    -   Исходного и финального размера (в токенах или байтах).
        
    -   Количества отброшенных чанков.
        
    -   Названия переменной, которая была обрезана (если применимо).
    
12. \[ \] **History Formatting:** Утилита `historyFormatter` корректно преобразует массив сообщений в структурированный Markdown формат с четким разделением реплик пользователя и ассистента (`User:` / `Assistant:`).
    
13. \[ \] **History Input Handling:** Обработчик `CMD_GEN_RESPONSE` корректно обрабатывает оба формата истории (массив сообщений и строку Markdown) и форматирует их перед передачей в Dify Workflow.
    
14. \[ \] **LLM Context Clarity:** Отформатированная история передается в Dify Workflow в структурированном виде, что обеспечивает корректное понимание LLM структуры диалога и предотвращает путаницу между репликами пользователя и оператора.
    
15. \[ \] **Main App Format:** Main App передает историю в виде массива сообщений (предпочтительно) или в виде структурированного Markdown с префиксами `User:` / `Assistant:`. Воркер корректно обрабатывает оба формата.
    
16. \[ \] **Format Validation:** Если Main App передает историю в виде строки, воркер проверяет наличие структурированного формата (префиксы `User:` / `Assistant:`) и логирует предупреждение при обнаружении "плоского" текста.
    
17. \[ \] **Prompt Engineering:** Системный промпт в узле LLM Workflow "Support Helper" явно указывает, что `{{history}}` — это история переписки с префиксами `User:` и `Assistant:`, а `{{context}}` — это релевантная информация из базы знаний, и как использовать эти данные для ответа на `{{query}}`. Без правильной связки в промпте передача истории и контекста неэффективна.
