

# Техническое задание: Настройка Тестирования и QA

**Контекст:** Микросервис содержит критически важную бизнес-логику (биллинг, синхронизация данных, External RAG) и асинхронные цепочки вызовов. Ручное тестирование очередей трудоемко и ненадежно. Необходимо внедрить автоматическое тестирование для гарантии стабильности.

**Цель:** Настроить тестовый фреймворк (Jest), реализовать моки для внешнего API Dify (jest.mock) и написать набор Unit и Integration тестов, покрывающих основные сценарии.

## 1\. Установка зависимостей

-   `jest`: Основной тестовый раннер.
    
-   `uuid`: Для генерации тестовых ID (опционально, если требуется).
    
**Примечание:** Для мокирования используется встроенный механизм Jest (`jest.mock`), который позволяет мокировать модули на уровне импортов. Это обеспечивает единый подход к тестированию во всем проекте.
    

## 2\. Конфигурация Jest (`jest.config.js`)

Создать конфиг в корне проекта.

**Требования:**

1.  **Environment:** `node`.
    
2.  **Test Match:** `**/tests/**/*.test.js` или `**/*.spec.js`.
    
3.  **Setup Files:** Создать файл `tests/setup.js`, который будет:
    
    -   Загружать `.env.test` (или устанавливать переменные окружения программно).
        
    -   Мокать логгер, чтобы тесты не засоряли консоль.
        
    -   Устанавливать таймауты (для интеграционных тестов BullMQ может потребоваться > 5 сек).
        

## 3\. Unit Тестирование (Изолированные модули)

Необходимо покрыть тестами утилиты и сервисы, не зависящие от Redis/Dify напрямую.

### 3.1 `tests/unit/utils/errorHandler.test.js`

-   **Цель:** Проверить маппинг ошибок.
    
-   **Сценарии:**
    
    -   Передать `AxiosError` (ECONNREFUSED) -> Ожидать `errorCode: NETWORK_ERROR`.
        
    -   Передать `DifyApiError` (404) -> Ожидать `errorCode` из ошибки или fallback.
        
    -   Передать `SyntaxError` -> Ожидать `errorCode: LLM_OUTPUT_PARSE_ERROR`.
        

### 3.2 `tests/unit/services/billingService.test.js`

-   **Цель:** Проверить извлечение токенов.
    
-   **Сценарии:**
    
    -   Передать JSON ответа Workflow (usage в outputs или metadata) -> Проверить цифры.
        
    -   Передать JSON без usage -> Проверить возврат 0 и дефолтной модели.
        

### 3.3 `tests/unit/utils/llmParser.test.js`

-   **Цель:** Проверить очистку JSON от Markdown.
    
-   **Сценарии:**
    
    -   Вход: `Here is json: \`\`\`json {"a":1} \`\`\``-> Корректный объект`{a:1}\`.
        

## 4\. Интеграционное Тестирование (Цепочка Воркеров)

Эти тесты поднимают реальные (или почти реальные) инстансы воркеров и очередей, используя локальный Redis.

**Подготовка (`tests/integration/helpers.js`):**

-   Функция `startTestApp()`: Подключается к Redis, чистит его (`flushdb`), инициализирует воркеры.
    
-   Функция `stopTestApp()`: Закрывает воркеры и Redis соединение.
    

### 4.1 `tests/integration/fastLane.test.js`

**Сценарий: Генерация ответа (External RAG Happy Path)**

1.  **Setup:**
    
    -   Использовать `jest.mock` для мокирования модулей:
        -   `jest.mock('../../src/infrastructure/dify/api')` - мокирование Dify API
        -   `jest.mock('../../src/infrastructure/bullmq/resultQueue')` - мокирование очереди результатов
        -   `jest.mock('../../src/infrastructure/redis/cache')` - мокирование Redis кэша
        -   `jest.mock('../../src/infrastructure/redis/client')` - мокирование Redis клиента
        
    -   Настроить моки для методов Dify API:
        -   `difyApi.retrieveChunks` -> Вернуть мокированные чанки для admin и history баз
        -   `difyApi.runWorkflow` -> Вернуть успешный ответ с текстом и usage
        
    -   Использовать `jest.spyOn` для мокирования `OrganizationService.getKbIdsOrThrow` -> Вернуть `{ adminKbId: 'kb-admin-1', historyKbId: 'kb-history-1' }`
        
2.  **Action:**
    
    -   Вызвать воркер напрямую с мокированным job объектом.
        
3.  **Assert:**
    
    -   Проверить, что `sendResult` был вызван с правильными данными.
        
    -   Проверить, что `status: 'success'`, текст ответа совпадает с моком, и `meta` вернулась.
        
    -   Проверить, что все методы Dify API были вызваны с правильными параметрами.
        

**Сценарий: Ошибка KB\_NOT\_FOUND**

1.  **Setup:** Настроить `jest.spyOn` для `OrganizationService.getKbIdsOrThrow` -> Выбросить `KbNotFoundError`.
    
2.  **Action:** Вызвать воркер с задачей для несуществующей организации.
    
3.  **Assert:** Проверить, что `sendResult` был вызван с `status: 'error'`, `errorCode: 'KB_NOT_FOUND'`. Убедиться, что методы Dify API не были вызваны.
    

### 4.2 `tests/integration/slowLane.test.js`

**Сценарий: Загрузка файла (Lazy Loading)**

1.  **Setup:** Использовать `jest.mock` для мокирования модулей. Настроить моки:
    
    -   `difyApi.listDatasets` -> Вернуть пустой список (базы нет).
        
    -   `difyApi.createDataset` -> Вернуть новый ID `kb-new`.
        
    -   `difyApi.createDocumentByFile` -> Вернуть успех.
        
    -   Мокировать `FileService.downloadFile` для скачивания файла.
        
2.  **Action:** Вызвать воркер с задачей `CMD_KB_ADD_FILE`.
    
3.  **Assert:**
    
    -   Проверить, что методы Dify API были вызваны в правильном порядке.
        
    -   Проверить результат: `status: 'success'`.
        

## 5\. Скрипты запуска

Добавить в `package.json`:

-   `"test"`: "jest"
    
-   `"test:watch"`: "jest --watch"
    

# Acceptance Criteria (Критерии приемки)

1.  \[ \] **Конфигурация:** `npm test` запускается успешно с `.env.test`.
    
2.  \[ \] **Unit Tests:** Утилиты (`errorHandler`, `billing`, `parser`) покрыты тестами.
    
3.  \[ \] **External RAG Test:** Тест `Fast Lane` проверяет **всю цепочку**: получение ID -> параллельный поиск (2 запроса) -> генерация (1 запрос с контекстом).
    
4.  \[ \] **Mocking:** Тесты **не делают** реальных сетевых запросов к Dify (используется `jest.mock` для мокирования модулей на уровне импортов).
    
5.  \[ \] **Redis Cleanup:** После прогона тестов база очищается.
